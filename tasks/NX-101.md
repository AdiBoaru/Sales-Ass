# NX-101 — Demand & Product Intelligence: rollup + raportul «Cerere & Produse»
**Owner:** S · **Faza:** P1 · **Zi/Ord:** track «Cerere & Produse», pasul 2 · **Branch:** `feat/NX-101-demand-intelligence` · **Complexitate:** L · **Estimare:** 4h *(>4h → vezi [PROPUNERE] de spargere)*

## Goal
Transformă evenimentele de cerere (NX-100) + datele existente (`orders`, `back_in_stock_subscriptions`,
`contacts.lead_score`) în **raportul de business pe care proprietarul îl deschide și ia decizii din
el** ([ANALYTICS-AUDIT-SI-BLUEPRINT.md](../docs/ANALYTICS-AUDIT-SI-BLUEPRINT.md) §4bis): *ce se vinde,
ce se caută, ce se cere, pe ce să consume bani, ce ar vrea clienții să găsească*. Un rollup nocturn
(ca `usage_daily`) + un strat de query care produce cele 5 secțiuni + recomandările derivate.

## Business Context
Asta e direcția cea mai valoroasă pentru retenție: botul ca **senzor de cerere**. Date pe care
comerciantul nu le ia din GA/ads — căutările eșuate și brandurile cerute-dar-neavute. Deblochează
restock prioritizat, extindere catalog, conținut PDP și gamă de preț. E argumentul prin care
clientul vede botul ca asset de merchandising, nu ca centru de cost.

## Technical Description

### Rollup nocturn `rollup_demand.py` (admin_conn — citește `analytics_events`)
Ca `rollup_usage.py`: `bot_runtime` NU are SELECT pe `analytics_events`, deci jobul rulează pe
`admin_conn`, cross-tenant peste businessurile active, idempotent (upsert pe zi). Filtrare
explicită `business_id = $1` în fiecare CTE (P7), fereastra zilei UTC pe `created_at`.

### Două tabele de agregare (DDL nou)
```sql
-- ce se vinde: contoare per produs/zi (din evenimentele NX-100 + orders)
create table product_demand_daily (
  business_id   uuid not null references businesses(id) on delete cascade,
  day           date not null,
  product_id    uuid not null,
  recommended   integer not null default 0,   -- din agent_recommended.product_ids
  added_to_cart integer not null default 0,   -- din cart_updated.product_ids
  checkout_incl integer not null default 0,   -- din checkout_link_created.product_ids
  attributed_orders   integer not null default 0,   -- orders atribuite ce conțin produsul
  attributed_revenue  numeric(14,2) not null default 0,
  primary key (business_id, day, product_id)
);
-- ce se cere și NU s-a găsit: semnătură normalizată per zi
create table unmet_demand_daily (
  business_id  uuid not null references businesses(id) on delete cascade,
  day          date not null,
  request_kind text not null,                 -- 'no_result' | 'out_of_stock' | 'price_gap'
  request_sig  text not null,                 -- semnătură normalizată: ex 'brand:bioderma' / 'cat:crema|band:sub_50'
  count        integer not null default 0,
  primary key (business_id, day, request_kind, request_sig)
);
create index idx_unmet_business_day on unmet_demand_daily(business_id, day desc);
```
`request_sig` = compunere deterministă din câmpurile normalizate ale `unmet_query` (NX-100) — NU
text brut (P12). Tabelele sunt mici (top-N pe zi) → fără partiționare.

### Stratul de query — cele 5 secțiuni (`src/db/queries/demand.py`)
Funcții `business_id`-scoped, parametrizate pe interval `[from, to]`:
1. **Top produse cerute & vândute** — `product_demand_daily` agregat pe interval + join `products`
   (name) → `{product, recommended, added_to_cart, attributed_orders, attributed_revenue, conv_rate}`.
2. **Top căutări & atribute** — agregare `product_search` (din `analytics_events`) pe
   `category`/`brand`/`concern_keys` → volum + `% cu rezultat` (count>0) + trend.
3. **Cerere neîmplinită** — `unmet_demand_daily` (no_result) ∪ produse out-of-stock cele mai cerute
   (join `products.availability` + `back_in_stock_subscriptions` ranked) → fiecare cu recomandarea
   derivată (`adu în catalog` / `reaprovizionează` / `adaugă entry-level`).
4. **Întrebări recurente (v1 grosier)** — agregare `faq_lookup` (miss) + `clarify_asked` pe câmp →
   „top întrebate". Clustering semantic real = **NX-102**.
5. **Buy-signals pierdute** — `contacts` cu `lead_score >= prag` care au eveniment de intenție
   (`intent_detected route in (sales,order)`) dar **fără** comandă atribuită în fereastră.

### Owner / scriere
Niciun câmp `TurnContext`. Jobul scrie DOAR în `product_demand_daily` / `unmet_demand_daily`
(owner exclusiv = rollup-ul). Stratul de query e read-only.

## Test Cases
**Happy Path:**
1. 1 produs recomandat de 5×, add-to-cart 2×, 1 comandă atribuită → rândul `product_demand_daily` corect; raportul 1 îl arată cu `conv_rate=20%`.
2. 3× `unmet_query{brand:bioderma}` → `unmet_demand_daily(no_result,'brand:bioderma',3)`; raportul 3 recomandă „adu în catalog".

**Edge Cases:**
1. Produs out-of-stock cu 4 abonări back-in-stock → apare în «cerere neîmplinită» chiar fără `unmet_query`.
2. Lead `lead_score=80` cu intenție sales dar comandă atribuită prezentă → NU apare în «buy-signals pierdute».
3. Zi fără evenimente de cerere → rapoarte goale, nu eroare.

**Failure Cases:**
1. Re-rulare aceeași zi → upsert idempotent, contoare nedublate.
2. `product_id` din eveniment care nu mai e în catalog (șters) → join lasă numele NULL/`(produs eliminat)`, nu crapă.
