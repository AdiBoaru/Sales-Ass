# NX-122 — Per-turn trace correlation: stamp turn_id + capture tool-call args/results

**Owner:** Claude · **Faza:** P1 · **Track/Wave:** Wave2 · **Branch:** `feat/NX-122-turn-trace-correlation` · **Complexitate:** M · **Estimare:** 4h

## Goal
Fiecare event de observabilitate emis într-un tur (stage_completed, llm_usage, tool_call, validator_rejected, agent_recommended...) primește `turn_id`-ul turului din care provine, ca să poți izola și REJUCA traiectoria unui singur mesaj inbound într-o conversație multi-tur. În plus, `tool_call` capturează args sanitizate (filtre/buget/categorie), numărul de rezultate și latența — ca să poți depana din analytics „de ce a căutat în categoria greșită" — iar downgrade-urile tăcute de la rich → proză devin vizibile printr-un event `rich_downgraded`.

## Business Context
Asistentul e un singur creier pe mai multe canale și mai multe verticale; calitatea retrieval-ului și a vânzării se reglează din date, nu din ghicit. Azi, într-o conversație cu 6 mesaje, toate event-urile au doar `business_id/conversation_id/contact_id` (analytics.py:37-44) — nu poți spune care `stage_completed`/`tool_call` aparțin cărui inbound, deci traiectoria nu e rejucabilă. `tool_call` salvează doar `{name, ok}` (agent.py:447) → nu vezi ce filtre a trimis modelul, câte produse au rezultat, cât a durat. Pentru un produs SaaS managed (reglaj per-client/per-vertical, debugging live-test, evals), tracing-ul corelat per-tur e linia de bază de observabilitate pe care 2026 o cere implicit. E vertical-agnostic; args mai bogate ajută și la tuning-ul retrieval-ului pe fiecare verticală.

## Technical Description

### 1. Stamp `turn_id` pe orice event
`TurnContext.turn_id` există deja (models.py:318) și e generat la intrarea în pipeline, dar `emit()` (models.py:346-348) nu îl injectează. Soluția: `emit()` adaugă `turn_id` în `properties` automat, fără ca stagiile să știe (principiul 10 — observabilitate din runner/context, nu din stagiu).

```python
def emit(self, type_: str, **properties: Any) -> None:
    properties.setdefault("turn_id", self.turn_id)
    self.events.append(Event(type=type_, properties=properties))
```

Persistăm `turn_id` și ca **coloană dedicată** pe `analytics_events` (extracție din properties în `insert_events`, exact ca pentru tokens/cost analytics.py:42-44) → filtrare ieftină și index pentru retrieval de traiectorie. `insert_events` extrage `e.properties.get("turn_id")` și îl scrie pe coloană (rămâne și în jsonb, cost zero, consistent cu tokens_in/out).

Adăugăm index `(business_id, conversation_id, created_at)` pentru a aduce toate event-urile unei conversații în ordine cronologică și a le grupa pe `turn_id` la replay.

### 2. `tool_call` îmbogățit (sanitizat, fără PII)
În `agent_stage.execute` (agent.py:436-448) măsurăm latența apelului și emitem args **whitelisted** + count + latență + clasă de eroare:

```python
async def execute(name: str, args: dict[str, Any]) -> str:
    started = perf_counter()
    result = await run_tool(ctx, deps, name, args)
    latency_ms = round((perf_counter() - started) * 1000, 1)
    ...
    ctx.emit(
        "tool_call", name=name, ok=result.ok,
        args=_safe_tool_args(name, args),       # whitelist per tool, fără PII
        n_results=len(result.products),
        latency_ms=latency_ms,
        error=(result.error if not result.ok else None),  # clasa de eroare (type(e).__name__), NU corpul
    )
    return ...
```

`_safe_tool_args(name, args)` = un helper (în agent.py sau `src/tools/base.py`) cu o **whitelist de chei per tool**, niciun fallback „pune tot ce e acolo" (principiul 12 — PII într-un singur loc; analytics nu primește text liber al userului):
- `search_products` → `{category, filters, budget_max, concerns, suitable_for, limit}` (scalari/liste scurte; valorile trunchiate la o lungime mică)
- `get_product_details` / `compare_products` → `{product_id(s)}`
- `check_order` → emite DOAR `{has_arg: bool}` (numărul de comandă / contactul = PII → niciodată în properties)
- `checkout_link` / `cart_add` → `{product_id, variant_id}`
- tool necunoscut → `{}`.

Channel-aware: identic pe web și WhatsApp — `tool_call` apare la fel pentru ambele tipuri de tur (calea agent e agnostică de canal). Diferența de randare (buton web vs CTA/text WhatsApp) NU atinge tracing-ul.

### 3. `rich_downgraded` — downgrade-uri tăcute vizibile
Pe calea SALES, dacă recomandarea bogată (model iZi) eșuează, codul cade tăcut pe proză (agent.py:511-525: dacă `rich is None or not rich.items`, intră pe ramura de proză fără niciun event). Emitem un event cu **motiv**:
- `reason="structured-call-failed"` — `_finalize_rich` a întors `None` (apelul structurat a eșuat / excepție).
- `reason="all-items-dropped-by-membership"` — a întors un rich cu `items == []` (toate produsele au picat la grounding-ul de apartenență).

```python
rich = await _finalize_rich(...)
if rich is not None and rich.items:
    ctx.set_rich_reply(...); ctx.emit("agent_recommended", n=..., rich=True); return
ctx.emit("rich_downgraded", reason=("all-items-dropped-by-membership" if rich is not None else "structured-call-failed"))
# ... cade pe proză (cod existent)
```

`rich_downgraded` moștenește automat `turn_id` din `emit()` → corelabil cu `tool_call`-urile aceluiași tur.

Rămâne append-only (botul are doar INSERT pe `analytics_events`, analytics.py:1-9). Reutilizăm disciplina de redaction existentă (clasa de eroare, nu corpul — vezi pattern-ul agent.py:468 `type(e).__name__`; validator_rejected agent.py:530 emite doar contorul).

## Principii CLAUDE.md aplicabile
- **P3 (single-owner-per-field):** `turn_id` are un singur scriitor (generat la intrare); `emit()` doar îl propagă, nu îl rescrie (`setdefault`, nu suprascrie un `turn_id` explicit).
- **P7 (business_id everywhere):** indexul și retrieval-ul de traiectorie sunt `business_id`-first; `insert_events` rămâne tenant-scoped (analytics.py:8).
- **P10 (observabilitate din runner):** stagiile nu știu că `turn_id` se injectează — se face în `emit()`; runner-ul/processor-ul scriu event-ul.
- **P12 (PII într-un singur loc):** args sunt whitelisted; numerele de comandă / contactele / corpul mesajului NU ajung în properties; erorile = clasă, nu corp.
- **P6 (never silent):** `rich_downgraded` face vizibil un downgrade care azi e tăcut (nu schimbă comportamentul către client, doar îl instrumentează).

## Test Cases
**Happy:** Un tur SALES cu rich reușit → toate event-urile (stage_completed × n, llm_usage, tool_call, agent_recommended) au același `turn_id == ctx.turn_id`; `tool_call` pentru `search_products` conține `args={category,filters,budget_max,...}` și `n_results>0` și `latency_ms>=0`. Două tururi consecutive pe aceeași conversație produc două seturi cu `turn_id` distincte.
**Edge:** `check_order` → `tool_call.args` NU conține numărul de comandă (doar `has_arg=True`); tool cu args vide → `args={}`. `rich is not None and items==[]` → `rich_downgraded reason="all-items-dropped-by-membership"`; `rich is None` → `reason="structured-call-failed"`. Event emis cu `turn_id` explicit în properties → `setdefault` NU îl suprascrie.
**Failure:** `run_tool` întoarce `ok=False` → `tool_call.error == result.error` (clasă), `n_results==0`, niciun corp/PII în properties. `insert_events` cu eveniment fără `turn_id` în properties → coloana primește NULL fără excepție (append-only nu crapă).
