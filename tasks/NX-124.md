# NX-124 — Knowledge & catalog filter correctness: taxonomy-from-DB + GIN index + cache/FAQ guards

**Owner:** Claude · **Faza:** P2 · **Track/Wave:** Wave3 · **Branch:** `feat/NX-124-knowledge-filter-correctness` · **Complexitate:** L · **Estimare:** 7h (vezi [PROPUNERE] split la final)

## Goal
Repară patru defecte de corectitudine în straturile gratuite + catalog: (1) maparea concern→cheie e hardcodată beauty-only (`taxonomy.py:58`) → orice alt vertical pică tăcut filtrele; (2) filtrul `attributes ?| concerns` riscă seq-scan (index GIN există dar nu e verificat sub `?|`); (3) lookup-urile cache+FAQ nu filtrează pe `embedding_model` → un upgrade de model amestecă spații vectoriale incompatibile; (4) cache embed-uiește `canonicalize(body)` iar FAQ embed-uiește `body` brut (normalizare inconsistentă, praguri necomparabile) și nu există fallback de locale → un user HU/EN cu cunoștințe seedate doar RO deflectă 0%.

## Business Context
Single-brain, multi-channel, multi-vertical: maparea concern hardcodată pe beauty e **blocant #1** pentru onboarding HVAC/auto/salon fără cod — un retailer HVAC care zice „zgomotos"/„economic" mapează la `{}` și primește filtre tăcut ignorate, deci recomandări irelevante din prima conversație. Fallback-ul de locale deblochează retailerii RO care servesc clienți HU în Transilvania (cunoștințe seedate RO, întrebări HU) — azi deflectă 0% acolo. Filtrarea pe `embedding_model` e o plasă de siguranță obligatorie înainte de orice upgrade de embeddings (altfel cache-ul devine zgomot și prețurile/răspunsurile se degradează silent). Pe WhatsApp inputurile sunt mai zgomotoase (emoji / ALL CAPS / fără diacritice) decât pe widget-ul web, deci paritatea de normalizare FAQ contează mai mult acolo.

## Technical Description

### 1. Taxonomie concern din DB (depinde de NX-114 DomainPack)
Azi `_BY_VERTICAL = {"beauty": _BEAUTY}` (`src/tools/taxonomy.py:58`) și `map_concerns(vertical, raw)` (`taxonomy.py:61`) — orice vertical ≠ beauty → tabel gol → `[]`. NX-114 introduce DomainPack ca config DB per-tenant/per-vertical. `map_concerns` devine `map_concerns(domain_pack, raw)`: citește maparea din `domain_pack.concern_map` (jsonb `{phrase_norm: canonical_key}`), păstrând EXACT semantica actuală — `_norm()` (strip diacritice + lower), necunoscutele ignorate (P6 indirect: mai bine zero filtru decât unul fals care golește rezultatul), chei unice sortate (determinist → prompt-cache-friendly). Beauty rămâne fallback hardcodat DOAR ca seed pentru DomainPack-ul demo (zero regresie). Caller: `src/tools/catalog_tools.py:146` (`concern_keys = map_concerns(...)`) primește domain pack-ul din `ctx` în loc de `ctx.business.vertical`.

### 2. Generalizare filtru attributes + index GIN
Filtrul actual e hardcodat pe cheia `concerns`: `(p.attributes->'concerns') ?| $N::text[]` (`catalog.py:131` și `catalog.py:336`). Generalizăm la chei arbitrare din DomainPack (HVAC: `noise_class`, auto: `fitment`) — un helper `_attr_filter(key, values)` care emite `(p.attributes->key) ?| $N::text[]` pentru fiecare grup de filtre din DomainPack, păstrând `?|` (oricare-din). Index: schema are deja `idx_products_attrs_gin … using gin(attributes)` (`schema_v2_production.sql:339`) — clasa `jsonb_ops` (default) SUPORTĂ `?|`/`?`/`@>`; `jsonb_path_ops` NU suportă `?|` (doar `@>`). Deci NU migrăm la `jsonb_path_ops` (ar rupe `?|`). Acțiunea reală: **verifică EXPLAIN** că `?|` chiar folosește indexul existent; dacă planner-ul preferă seq-scan pe predicate compuse, adaugă index expresie țintit pe sub-cheile fierbinți din DomainPack (`gin((attributes->'concerns'))`). Migrarea documentează ce s-a adăugat + dovada EXPLAIN.

### 3. Guard embedding_model pe cache + FAQ
`semantic_cache.embedding_model` există (migrarea `006_semantic_cache_v2.sql:16`) dar e **coloană moartă**: `exact_lookup`/`semantic_lookup` (`semantic_cache.py:53,83`) NU o filtrează — un upgrade `text-embedding-3-small → -3-large` (dim diferită) sau orice schimbare de model amestecă spații vectoriale. Adăugăm `and embedding_model = $N` în ambele lookup-uri (param din `get_settings().model_embed`, `config.py:38`). `faqs` NU are coloana → migrarea o adaugă (`add column if not exists embedding_model text not null default 'text-embedding-3-small'`) + filtru în `faqs.semantic_lookup` (`faqs.py:36`). Alternativ acceptat: la migrarea de model, purge cache + re-embed FAQ; alegem filtrul (mai sigur, zero downtime de deflecție).

### 4. Paritate de normalizare FAQ + fallback de locale
Cache-ul embed-uiește `canonicalize(body)` (`cache.py:105`, `src/cache/canonical.py:65`) dar FAQ-ul embed-uiește `body` brut (`faq.py:41`, `faq_tools.py:38`). Inconsistența face `faq_tau_high`/`faq_tau_tool` necomparabile cu pragurile de cache. Aliniem: `faq_stage` și `faq_lookup_tool` embed-uiesc `canonicalize(body)[0]`, iar **re-embedding-ul seed-ului FAQ** trebuie să folosească aceeași normalizare (`src/jobs/seed_faqs.py`) — altfel query-ul normalizat nu mai matchează vectorii bruți stocați. Re-tunăm `faq_tau_high`/`faq_tau_tool` empiric după paritate. Fallback locale (config-gated, `faq_locale_fallback_enabled`): la miss pe `ctx.language`, dacă `ctx.language ≠ business.default_locale` ȘI fallback-ul e activ, repetă lookup-ul pe `business.default_locale` cu prag mai STRICT (precision-first, same-language-family doar — NU traducem, doar servim cunoștința RO unui user care a scris în RO dar conv.locale e HU). Emit eveniment `locale_unserved` când nici fallback-ul nu prinde (semnal de seedat cunoștințe în acea limbă). Pe WhatsApp (input zgomotos) paritatea de normalizare ridică recall-ul mai mult decât pe web — comportament identic în cod, doar efectul diferă.

## Test Cases
**Happy:**
- HVAC DomainPack cu `concern_map={"zgomotos":"low_noise"}`: `map_concerns(pack, ["zgomotos"]) == ["low_noise"]`; `search_products` aplică `attributes->'concerns' ?| ['low_noise']`.
- Beauty neregresie: `map_concerns(beauty_pack, ["ten gras","sensibil"]) == ["oily","sensitive"]` (sortat).
- User cu `conv.locale='hu'`, cunoștințe seedate doar `ro`, fallback ON: lookup HU miss → fallback RO prag-strict → hit, deflectă.

**Edge:**
- Concern necunoscut (`"verde fluorescent"`) → `[]`, query fără clauză attributes (nu golește rezultatul).
- Input WhatsApp zgomotos `"CÂT E LIVRAREA??? 📦"` → `canonicalize` colapsează la aceeași cheie ca `"cat e livrarea"`; FAQ hit identic ca web.
- Două entry-uri cache cu același `(business_id, locale, canonical_hash)` dar `embedding_model` diferit: lookup pe modelul curent întoarce DOAR pe al lui.
- Fallback ON dar `ctx.language == business.default_locale`: NU face al doilea lookup (no-op, fără cost dublu).

**Failure:**
- Migrarea neaplicată (`faqs.embedding_model` lipsă) → `faq_stage` prinde excepția → miss grațios, NU rupe turul (P6).
- DomainPack lipsă pentru tenant → fallback la seed beauty/`{}` fără crash.
- EXPLAIN arată seq-scan după index expresie → DoD nereușit, re-evaluează predicate compuse.
