# NX-99 — Fix critic: rollup cost/token din `messages`, nu din `analytics_events`
**Owner:** S · **Faza:** P1 · **Zi/Ord:** Phase 0 (înaintea oricărui dashboard) · **Branch:** `fix/NX-99-rollup-cost-from-messages` · **Complexitate:** S · **Estimare:** 2-3h

## Goal
`usage_daily` e documentată ca **singura sursă pentru facturare + dashboard**, dar coloanele
`tokens_in/out` și `cost_usd` sunt structural **0**. Rollup-ul le calculează ca `SUM` peste
coloanele dedicate din `analytics_events` ([usage.py:21-24](../src/db/queries/usage.py)), pe care
`insert_events` le populează **doar dacă** `event.properties` conține `tokens_in/out/cost_usd`
([analytics.py:42-44](../src/db/queries/analytics.py)) — dar **niciun `emit()`** din pipeline nu
atașează acele chei. Adevărul de cost trăiește pe `messages.cost_usd` + `messages.tokens_in/out`
([messages.py](../src/db/queries/messages.py)), pe care rollup-ul **nu le citește pentru cost**.
Taskul repointează agregarea de cost/token pe `messages`. Vezi
[ANALYTICS-AUDIT-SI-BLUEPRINT.md](../docs/ANALYTICS-AUDIT-SI-BLUEPRINT.md) §1.2 Defect 1.

## Business Context
Costul e linia CFO: fără el, orice cifră de ROI / payback / cost-per-conversație de pe dashboard
e 0 sau falsă, iar facturarea per-tenant pe consum nu are bază reală. E prerequisitul Phase 0 —
nimic din stratul de bani nu e credibil până nu se repară.

## Technical Description
În `_ROLLUP_SQL` ([usage.py:18-86](../src/db/queries/usage.py)), CTE-ul `ev` agregă azi din
`analytics_events`:
```sql
coalesce(sum(tokens_in), 0)  as tokens_in,
coalesce(sum(tokens_out), 0) as tokens_out,
coalesce(sum(cost_usd), 0)   as cost_usd,
```
Mută aceste trei sume într-un CTE `cost` peste `messages` (sursa reală), păstrând fereastra zilei
UTC și filtrul pe `business_id` (P7):
```sql
cost as (
    select
        coalesce(sum(tokens_in), 0)  as tokens_in,
        coalesce(sum(tokens_out), 0) as tokens_out,
        coalesce(sum(cost_usd), 0)   as cost_usd
    from messages
    where business_id = $1
      and (created_at at time zone 'UTC')::date = $2
),
```
și în `insert ... select` înlocuiește `ev.tokens_in/out`, `ev.cost_usd` cu `cost.tokens_in/out`,
`cost.cost_usd`. CTE-ul `ev` rămâne pentru `conversations` (distinct conversation_id), `cache_hits`
și `handoffs` — acelea sunt corecte. `messages.cost_usd` e `numeric` și e deja scris de Sender
pe mesajele outbound LLM, deci suma reflectă costul real al turului.

**Notă de consistență:** `messages` e partiționat pe `created_at`; filtrul pe interval de zi
folosește deja `created_at` (cheia de partiționare) → partition pruning, fără scanare globală.
Rollup-ul rulează pe `admin_conn` (deja citește `analytics_events`/`orders` cross-grant), deci are
SELECT pe `messages`.

## Principii CLAUDE.md aplicabile
- **P7 (business_id pe tot):** CTE-ul nou filtrează explicit `where business_id = $1`.
- **P4/Observabilitate:** sursa de adevăr pentru cost = `messages` (unde Sender scrie real
  `cost_usd`/`tokens`), nu un câmp de eveniment niciodată populat.
- **P12 (PII):** `messages.body` NU e atins — doar agregarea numerică `cost_usd/tokens`.

## Implementation Steps
1. `src/db/queries/usage.py`: adaugă CTE `cost` peste `messages`; scoate `tokens/cost` din `ev`;
   repointează `select`-ul final pe `cost.*`.
2. `tests/test_rollup_usage_sql.py` (nou, `@pytest.mark.integration`, DB reală ca `test_analytics.py`):
   seedează un business throwaway, inserează 1 conversație cu N `messages` outbound cu `cost_usd`
   cunoscut → rulează `rollup_usage_day` → assert `usage_daily.cost_usd` = suma reală (nu 0).
3. Verifică că testul existent `tests/test_rollup_usage.py` (orchestrare, monkeypatch) rămâne verde.
4. `ruff check . && ruff format . && pytest -x -q` verde.

## Test Cases
**Happy Path:**
1. 3 mesaje outbound cu `cost_usd` 0.002/0.003/0.001 într-o zi → `usage_daily.cost_usd = 0.006`.
2. Tokens: `sum(tokens_in)`/`sum(tokens_out)` din `messages` egale cu valorile inserate.

**Edge Cases:**
1. Zi fără mesaje LLM (doar inbound / early-exit gratuit) → `cost_usd = 0` (coalesce), nu NULL.
2. Mesaje cu `cost_usd` NULL (non-LLM) → ignorate de `sum`, nu rup agregarea.

**Failure Cases:**
1. Re-rulare pe aceeași zi (idempotent upsert) → aceeași valoare, nu dublată.
2. Două businessuri în aceeași zi → fiecare rând are doar costul propriu (izolare pe business_id).
