# NX-141 — Scalare: eliberează conexiunea DB pe durata apelurilor LLM (turn phasing)

**Owner:** Claude · **Faza:** P1 · **Track/Wave:** Scalability · **Branch:** `feat/NX-141-conn-phasing` · **Complexitate:** L · **Estimare:** 2-3 zile (epic, feliat)

## Goal
Ridică plafonul de concurență al sistemului: azi un tur ține o conexiune din `bot_pool` (max_size=10) pe TOATĂ durata pipeline-ului, inclusiv 1-4 apeluri LLM de ordinul secundelor. Rezultat: max ~10 tururi concurente per proces worker, iar pooler-ul Supabase e capat la ~15 sesiuni. Ținta: conexiunea DB e ținută doar cât se citește/scrie efectiv — concurența devine limitată de LLM/CPU, nu de pool.

## Business Context
La 30+ conversații simultane (un singur client mediu pe WhatsApp la oră de vârf), tururile stau la coadă pe pool-ul de DB deși LLM-ul ar putea procesa în paralel — latență artificială care crește liniar cu traficul. Pentru un SaaS multi-tenant pe un VPS 1vCPU/4GB, ăsta e bottleneck-ul #1 identificat de audit (`docs/ARCHITECTURE-WORKFLOWS.md` § „Puncte slabe #5"), înaintea oricărei optimizări de model sau cache.

## Technical Description

### Cauza
- `handle_turn` primește `conn` și îl pasează prin `PipelineDeps` întregului pipeline (`src/worker/processor.py:528`); stagiile LLM (triage, agent — cu tool-loop de până la 3 pași + retry validator) rulează cu conexiunea checkout-ată.
- `bot_pool`: `max_size=10` (`src/db/connection.py:224-229`).
- Calea sincronă `/web/chat` ține conexiunea pe tot request-ul (`src/web/app.py:223-243`).
- Post-turul (cache writeback + summarizer + profil = până la 3 apeluri nano + 1 embed) rulează TOT pe aceeași conexiune, DUPĂ ce reply-ul a fost pus în outbox (`src/worker/processor.py:689-699`).

### Soluția — fazare, feliată în pași livrabili independent
**Felia 1 (ieftină, câștig imediat): post-turul pe conexiune proprie.**
Mută `_cache_writeback` + `_summarize_if_needed` + `_extract_profile_and_score` în afara checkout-ului principal: după TX-ul de outbox, release conn; post-turul face propriul `tenant_conn` scurt (sau task async separat). Taie ~30-50% din timpul de deținere fără să atingă pipeline-ul.

**Felia 2: tool-urile re-achiziționează conexiunea per query.**
`PipelineDeps.conn` devine un `ConnFactory` (callable → context manager `tenant_conn(business_id)`), tool-urile și stagiile fac checkout scurt per operație DB (search, faq lookup, cache lookup). Apelurile LLM rulează fără nicio conexiune deținută. Atenție la locurile care depind de aceeași conexiune (savepoint-uri, tranzacții) — TX-ul final al Sender-ului rămâne pe UN checkout dedicat.

**Felia 3: fazează `handle_turn` explicit.**
(a) READ-phase: claim dedupe + contact/conv + history/state/summary → release; (b) COMPUTE: pipeline cu ConnFactory; (c) WRITE-phase: checkout proaspăt → TX outbox + state + mark_completed. Invariante păstrate: claim-or-resume rămâne valid peste faze (claim-ul e durabil în DB, nu pe conexiune).

### Riscuri / ce NU se schimbă
- Izolarea NU slăbește: fiecare checkout trece prin `tenant_conn` cu assert (`connection.py:261-294`) — de fapt crește frecvența verificării.
- Optimistic lock pe state (`state_version`) protejează deja write-phase-ul contra curselor între faze.
- `deliver=False` (web sync) beneficiază identic — request-ul HTTP nu mai ține conexiunea prin LLM.
- Alternativa tactică respinsă: mărirea `max_size` — mută problema în pooler-ul Supabase (cap ~15 sesiuni, observat live pe sim).

## Principii CLAUDE.md aplicabile
- **P4 (buget impus în cod):** plafonul de conexiuni devine explicit gestionat, nu un efect emergent.
- **P7 (business_id pe tot):** ConnFactory poartă business_id-ul; fiecare re-checkout re-trece prin assert-ul de izolare NX-04.
- **P3 (un owner per câmp):** fazarea nu schimbă ownership-ul — doar momentul deținerii conexiunii.

## Implementation Steps
1. **Felia 1:** post-tur pe `tenant_conn` propriu; măsoară timpul de deținere înainte/după (event `turn_over_budget` are deja latențe per stagiu).
2. **Felia 2:** introdu `ConnFactory` în `PipelineDeps` (backward-compat: dacă `conn` e dat, factory-ul îl întoarce pe el — testele existente nu se ating); migrează tool-urile + stagiile free-layer.
3. **Felia 3:** split `handle_turn` în `_load_turn / _run_turn / _commit_turn`; TX-ul final identic byte-cu-byte.
4. Load-test pe sim harness (`scripts/sim/`): 30 conversații concurente, compară p95 înainte/după.
