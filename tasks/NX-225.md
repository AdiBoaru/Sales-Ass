# NX-225 — Timeout pe embed-ul de query: degradare la lexical-only și pe LENTOARE, nu doar pe eșec

**Owner:** Claude (build) / Codex (verify) · **Faza:** Web pilot · **Zi/Ord:** track B, 2 · **Branch:** `feat/NX-225-embed-timeout` · **Complexitate:** XS · **Estimare:** 1.5h
**Model recomandat:** Opus 4.8

## Goal
`embed([a.query])` are try/except cu cădere pe lexical-only
([catalog_tools.py:710-717](../src/tools/catalog_tools.py#L710-L717)) — dar un API de
embeddings care răspunde în 8 secunde NU aruncă excepție: ține tot turul, deși drumul de
degradare există la o excepție distanță. Taskul pune un timeout explicit pe apel; la
depășire, aceeași degradare grațioasă ca la eroare + telemetrie.

## Business Context
Pe web, clientul stă cu ochii pe typing indicator. Coada de latență a unui furnizor extern
nu are voie să devină coada de latență a chat-ului nostru, când avem deja un picior lexical
complet funcțional care răspunde în milisecunde.

## Technical Description
```python
# NX-225: lentoarea furnizorului = același drum ca eșecul lui (P6). wait_for anulează
# corect corutina la timeout (clientul OpenAI async suportă cancel).
query_vec: list[float] | None = None
if deps.llm is not None and await has_embeddings(deps.conn, ctx.business.id):
    try:
        query_vec = (
            await asyncio.wait_for(
                deps.llm.embed([a.query]),
                timeout=get_settings().embed_timeout_ms / 1000,
            )
        )[0]
    except TimeoutError:
        ctx.emit("embed_timeout", timeout_ms=get_settings().embed_timeout_ms)
        query_vec = None
    except Exception:  # noqa: BLE001 — comportamentul existent (eroare → lexical-only)
        query_vec = None
```
- `embed_timeout_ms` în `Settings` (Pydantic), **default 800** (p99-ul normal al
  `text-embedding-3-small` e sub ~500ms; 800 lasă loc de jitter fără să doară UX-ul).
  `0` = dezactivat (fără timeout — comportamentul de azi), ca să existe kill-switch numeric
  fără flag separat.
- Python 3.12: `asyncio.wait_for` ridică `TimeoutError` builtin — nu `asyncio.TimeoutError`
  (alias, dar prindem builtin-ul).
- Emitem event DOAR pe timeout (excepțiile rămân tăcute cum sunt azi? NU — vezi lecția
  „silent dead free layers": adăugăm și `embed_failed` pe ramura de excepție, cu
  `error_type=type(e).__name__`, fără mesaj/PII). Două semnale distincte: lent vs mort.
- Scopul e DOAR calea de căutare din `search_products_tool`. Embed-urile straturilor
  gratuite (cache semantic / FAQ) au propriile drumuri — vezi Out of Scope.

**TurnContext:** niciun câmp nou.
**Cost per 1000 mesaje:** zero cost nou (taskul doar LIMITEAZĂ timpul pierdut pe un apel
deja existent; niciun apel suplimentar).

## Out of Scope
- Timeout-uri pe embed-urile din cache semantic / FAQ lookup (stagiul 4) — aceeași
  problemă, alt loc; card separat dacă telemetria arată nevoia.
- Circuit breaker per furnizor (deschis după N timeouts) — se decide pe datele
  `embed_timeout` din pilot, nu preventiv.
- Retry pe timeout (un query de căutare nu merită a doua șansă lentă — lexicalul e deja bun).

## Test Cases
**Happy Path**
1. Embed în 5ms → semantic activ, niciun event nou.
2. Embed în > timeout → rezultate lexicale corecte + event.

**Edge Cases**
1. Timeout exact la limită (sleep ≈ timeout) → oricare ramură e acceptată, dar NICIODATĂ
   excepție nepredicată spre pipeline (testul rulează de mai multe ori? nu — sleep 2×
   timeout, determinist).
2. `has_embeddings` False → embed-ul nu se apelează deloc (drumul existent, neatins).

**Failure Cases**
1. Corutina anulată de `wait_for` aruncă `CancelledError` intern → nu scapă în tur (test:
   fake embed cu `try/finally` care loghează cancel-ul).
2. Settings lipsă (env vechi) → default 800 din Pydantic, fără crash la boot.

ZERO apeluri OpenAI reale în CI (fake LLM cu sleep).
