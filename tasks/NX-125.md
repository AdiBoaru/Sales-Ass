# NX-125 — Converge cost guard onto precise per-turn cost + per-contact/visitor spend cap

**Owner:** Claude · **Faza:** P2 · **Track/Wave:** Wave2 · **Branch:** `feat/NX-125-cost-guard-converge` · **Complexitate:** M · **Estimare:** 4h

## Goal
Alimentează contorul zilnic de cost (G2c) cu costul EXACT pe tur (`ctx.usage.cost_usd`, deja calculat din token usage real de runner), nu cu euristica grosieră `estimate_turn_cost`, astfel încât plafonul să se declanșeze la EXACT cifra pe care o arată `usage_daily`/dashboard. Elimină fereastra TOCTOU din `cost_over_budget`→`cost_add` folosind `INCRBYFLOAT`-then-compare. Adaugă un plafon SOFT de cheltuială per-contact (și per-vizitor web), reutilizând `incr_window`. Opțional, reseedează contorul zilei la boot din `usage_daily` ca să supraviețuiască pierderii Redis.

## Business Context
Asistentul e un singur creier multi-canal, multi-vertical, livrat ca serviciu managed pe retainer lunar. Economia retainerului depinde de un plafon de cost PRECIS: dacă guard-ul se declanșează la o cifră care nu se potrivește cu dashboard-ul, fie ardem peste plafon (pierdem marjă), fie tăiem LLM-ul prematur (degradăm clientul fără motiv). Astăzi există DOUĂ cifre paralele: euristica de event-counting (`estimate_turn_cost`, `limits.py:69-83`) vs. costul real din tokeni (`ctx.usage.cost_usd`, `runner.py:81`). Tool-calling-ul (G7) face 2-4× apeluri mini/tur cu lungimi de prompt foarte variabile — euristica „×(1 + nr tool_call)" cu cost fix pe apel deviază arbitrar de cifra reală.

În plus, plafonul e DOAR per-zi-per-business: o singură conversație în buclă sau un vizitor web abuziv poate arde plafonul întregului tenant. Web-ul e anonim și cu risc de abuz mai mare decât WhatsApp-ul gardat de Meta (NX-120) — un plafon de cheltuială per-vizitor contează mai mult acolo. Contorul trăiește doar în Redis (pierdut la FLUSHALL → resetează la 0 → plafon ocolit pentru tot restul zilei).

## Technical Description

### 1. Cost exact pe tur (deprecate `estimate_turn_cost`)
Runner-ul setează `ctx.usage = TurnUsage(..., cost_usd=acc.cost_usd, ...)` la `runner.py:77-88`, unde `cost_usd` e suma pe apeluri din token usage real (tokeni cached la tarif redus). `_record_turn_cost` (`processor.py:313-329`) rulează la `processor.py:457`, DUPĂ `run_pipeline` (`processor.py:455`) — deci `ctx.usage` e deja populat acolo.
- Înlocuiește `cost = estimate_turn_cost(ctx.events, ...)` cu `cost = ctx.usage.cost_usd if ctx.usage else 0.0`. Fallback `0.0` (turul fără apeluri LLM — cache L1/gates — nu acumulează, corect).
- `estimate_turn_cost` rămâne în `limits.py` DOAR ca „plafon pre-LLM" (ceiling estimat înainte de a apela LLM-ul, opțional pentru pre-check); marcat `# DEPRECATED pentru contorizare; folosit doar ca ceiling pre-LLM`. Nu mai e folosit pentru `cost_add`. (NU-l ștergem ca să nu rupem G2c/NX-54 care-l importă; un follow-up îl poate elimina.)
- Costurile best-effort din afara runner-ului rămân la euristica per-apel (corect, n-au `ctx.usage`): summarizer `processor.py:213`, profil `processor.py:251`, vision `gates.py:199` — acestea adaugă `settings.cost_*_usd` direct și nu se ating.

### 2. Elimină TOCTOU (read-then-write non-atomic)
Azi: `cost_over_budget` face `GET` (`limits.py:55`), apoi mai târziu `cost_add` face `INCRBYFLOAT` (`limits.py:65`) — două operații separate, fereastră în care N tururi concurente trec toate de check înainte ca vreunul să scrie (overshoot). Adaugă o primitivă atomică:
```python
async def cost_add_and_total(redis, key_or_business_id, amount_usd) -> float:
    """INCRBYFLOAT + EXPIRE; întoarce noul total. Compară DUPĂ increment → fără TOCTOU."""
```
`cost_over_budget` rămâne pentru pre-check-ul ieftin (`_llm_within_budget`, `processor.py:302` — un read e ok ca gate înainte de a cheltui), dar enforcement-ul real se mută POST-increment: după ce adăugăm costul turului, dacă noul total ≥ cap, emitem `cost_guard_tripped` și marcăm `state` ca să sărim LLM-ul la TURUL URMĂTOR. Astfel chiar dacă mai multe tururi concurente scapă de pre-check, increment-ul atomic înregistrează totalul corect și următorul tur e blocat determinist.

### 3. Plafon per-contact / per-vizitor (refolosește `incr_window`)
`incr_window` (`limits.py:34-41`, fereastră fixă cu EXPIRE) e deja primitiva generică (folosită de rate-limit contact + web NX-20). Adaugă o variantă pe cost:
```python
async def spend_over_cap(redis, scope_key, amount_usd, cap_usd, window_s) -> bool:
    """INCRBYFLOAT pe `spend:{scope_key}` (+EXPIRE la primul), compară cu cap. Atomic."""
```
- `scope_key` e neutru de canal: `f"{business_id}:contact:{contact_id}"` pe canale identificate (WhatsApp/Telegram) și `f"{business_id}:visitor:{sender_external_id}"` pe web (unde `sender_external_id` = token vizitor / IP, vezi `processor.py:389`). Pipeline-ul rămâne agnostic de canal (P1) — diferența e doar alegerea cheii de scope în processor, din `channel_kind`.
- SOFT cap: la depășire NU tăcem (P6) — emitem `contact_spend_capped`, dezactivăm LLM pentru acel contact restul ferestrei (cache L1 + gates servesc în continuare), iar reply-ul degradează grațios (triaj/agent fără LLM → echo/clarify, exact ca guard-ul de business).
- Default-uri în `settings`: `contact_daily_cost_cap_usd` (canale identificate, fereastră 24h) și `web_visitor_cost_cap_usd` + `web_visitor_cost_window_s` (web, fereastră mai scurtă, ex. 1h — abuz anonim). 0/None = dezactivat (per-vertical/tenant tunabil; generic peste verticale).

### 4. Reseed la boot (supraviețuiește pierderii Redis) — opțional, fail-soft
La pornirea worker-ului, dacă cheia `cost:{business}:{today}` lipsește, seed din sursa durabilă: `usage_daily.cost_usd` pentru ziua curentă (rollup nocturn poate fi stale → mai bine reagregă `analytics_events` cu `event_type='llm_usage'` pe azi dacă există). Best-effort: eșec → log + continuă (nu blochează boot-ul). Implementat ca funcție în `limits.py` apelată din consumer/processor la prima atingere a businessului pe ziua respectivă (lazy seed, marcat cu o cheie-santinelă `cost_seeded:{business}:{today}` ca să nu reseedăm la fiecare tur).

### 5. Ceiling de tokeni pe tur (agent runner)
În `LLMClient` (`src/agent/llm.py`) apelurile chat NU au `max_tokens` (excepție: `describe_image` `llm.py:245`). Un prompt patologic / buclă de output poate genera completion-uri lungi. Adaugă `max_completion_tokens` (configurabil, `settings.max_turn_completion_tokens`) pe `complete`, `complete_schema`, `run_tool_loop` — un ceiling dur pe output, independent de plafonul de cost. Conservator (ex. 800) ca să nu taie răspunsuri normale.

## Principii CLAUDE.md aplicabile
- **P2 (LLM doar la triaj+agent):** cost guard-ul rămâne cod determinist; nu adaugă apeluri LLM. Reseed citește DB/Redis, nu LLM.
- **P5 (un singur punct de ieșire):** guard-ul declanșat NU trimite alt mesaj — doar setează `llm=None`, reply-ul iese tot prin outbox.
- **P6 (niciodată tăcere):** soft cap → degradare (LLM off, cache+gates servesc), nu tăcere. Eșec Redis pe check → fail-open; eșec pe add → log, turul a răspuns deja.
- **P7 (business_id pe tot):** toate cheile (`cost:`, `spend:`, `cost_seeded:`) includ `business_id`; `usage_daily`/`analytics_events` la reseed filtrate pe `business_id`.
- **P10 (observabilitate din runner):** costul vine din `ctx.usage` agregat de runner (`runner.py:77`); processor-ul doar îl consumă. Stagiile nu știu de cost guard.
- **P11 (locale în chei):** N/A direct, dar `spend_over_cap` e ortogonal de locale.
- **P12 (PII într-un loc):** `scope_key` web folosește `sender_external_id` (token/IP) — deja în envelope, NU telefon; evenimentele logă DOAR chei/contoare, niciodată corpul mesajului sau telefon.

## Implementation Steps
1. `src/worker/limits.py`: adaugă `cost_add_and_total(redis, business_id, amount_usd) -> float` (INCRBYFLOAT + EXPIRE `_COST_KEY_TTL_S`, return total) și `spend_over_cap(redis, scope_key, amount_usd, cap_usd, window_s) -> bool` (INCRBYFLOAT pe `spend:{scope_key}` + EXPIRE la primul increment, compară cu cap). Marchează `estimate_turn_cost` ca DEPRECATED-for-counting în docstring.
2. `src/worker/limits.py`: adaugă `seed_daily_cost(admin_or_tenant_conn, redis, business_id) -> None` (lazy, santinelă `cost_seeded:{business}:{today}`; citește `usage_daily.cost_usd` azi sau reagregă `analytics_events`; best-effort).
3. `src/worker/processor.py:_record_turn_cost`: înlocuiește `estimate_turn_cost(...)` cu `ctx.usage.cost_usd if ctx.usage else 0.0`; folosește `cost_add_and_total`; dacă noul total ≥ cap, emite `cost_guard_tripped` (post-increment, determinist pentru turul următor).
4. `src/worker/processor.py:handle_turn`: după `_record_turn_cost`, aplică `spend_over_cap` pe `scope_key` derivat din `channel_kind` (contact vs visitor) cu costul turului; la depășire emite `contact_spend_capped` și persistă semnal în `state` ca turul următor să pornească cu LLM off pentru acel scope.
5. `src/worker/processor.py:_llm_within_budget`: adaugă check-ul soft per-contact/visitor lângă cel de business (pre-check ieftin); apel lazy `seed_daily_cost` la prima atingere a businessului pe zi.
6. `src/config.py`: adaugă `contact_daily_cost_cap_usd`, `web_visitor_cost_cap_usd`, `web_visitor_cost_window_s`, `max_turn_completion_tokens` (default-uri conservatoare; 0/None = off).
7. `src/agent/llm.py`: adaugă `max_completion_tokens=settings.max_turn_completion_tokens` (când >0) pe `complete`, `complete_schema`, `run_tool_loop` (toate apelurile `chat.completions.create` care produc răspunsul final/intermediar).
8. `tests/test_cost_guard.py`: adaugă cazurile de mai jos (fake redis cu suport `incrbyfloat`/`get`/`expire`; monkeypatch pe `ctx.usage`).
9. `ruff check . && ruff format . && pytest -x -q` verde.

## Test Cases
**Happy:**
- Tur cu `ctx.usage.cost_usd=0.0042` → `cost_add_and_total` adaugă exact `0.0042` (nu cifra euristică); totalul Redis = cifra agregată reală.
- `cost_add_and_total` întoarce noul total corect după două adăugări consecutive (0.01 + 0.02 = 0.03).
- `spend_over_cap` sub plafon → `False`, peste plafon → `True`; cheia `spend:{biz}:contact:{id}` capătă EXPIRE la primul increment.
- Web: `channel_kind='web'` → scope_key folosește `visitor:{sender_external_id}`; canal identificat → `contact:{contact_id}`.
- `seed_daily_cost`: cheie lipsă + `usage_daily.cost_usd=1.50` azi → contor Redis seedat la 1.50; santinelă setată, al doilea apel = no-op.

**Edge:**
- Tur fără apeluri LLM (`ctx.usage is None`, cache L1/gates) → cost 0, contor neatins, niciun event de cost.
- `max_turn_completion_tokens=0` (default off) → apelurile chat NU primesc `max_completion_tokens` (comportament neschimbat).
- Plafon `cap_usd=None`/0 (contact sau business) → guard dezactivat, fail-open.
- Concurență: două tururi POST-increment — totalul cumulativ corect; al doilea tur care depășește emite `cost_guard_tripped` (fără overshoot necontorizat).

**Failure:**
- Redis `incrbyfloat` aruncă în `_record_turn_cost` → log warning, turul a răspuns deja (best-effort), fără excepție propagată.
- Redis `get` aruncă în `cost_over_budget` (pre-check) → fail-open, LLM rulează normal.
- `seed_daily_cost`: query `usage_daily` aruncă → log + continuă, contorul rămâne ne-seedat (acceptat, nu blochează boot-ul).
- `spend_over_cap` aruncă → fail-open pe scope (nu blochează contactul din cauza unui Redis indisponibil).
