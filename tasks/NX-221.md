# NX-221 — Serializare ture per conversație pe web + reply-ul NU se pierde la conflict de stare

**Owner:** Claude (build) / Codex (verify) · **Faza:** Web pilot (P0 înainte de trafic real) · **Zi/Ord:** track A, 1 · **Branch:** `fix/NX-221-web-turn-lock` · **Complexitate:** M · **Estimare:** 4h
**Model recomandat:** Fable 5 (concurență + tranzacții — clasa NX-204/209)

## Goal
Două mesaje trimise rapid pe `/web/chat` în aceeași conversație rulează azi două pipeline-uri
CONCURENTE pe același snapshot de stare. Plasa existentă e doar optimistic lock la persistare
([conversations.py:117-144](../src/db/queries/conversations.py#L117-L144)), iar excepția
`StateVersionConflict` se aruncă ÎN aceeași tranzacție în care s-a scris deja răspunsul
([processor.py:472-488](../src/worker/processor.py#L472-L488)) — pe cod, turul care pierde își
pierde și reply-ul, nu doar patch-ul de stare. Taskul introduce serializare per conversație
(lock Redis scurt) + tratarea conflictului astfel încât NICIUN tur să nu rămână fără răspuns.

## Business Context
Pe web, clientul scrie des în rafale („serum pentru ten gras" … „sub 100 lei"). Fără serializare,
la trafic real vom avea răspunsuri corecte individual dar atașate mesajului greșit, sesiuni de
căutare suprascrise aleator și — în cazul conflictului — întrebări rămase fără răspuns. Erori
nereproductibile exact în demo-urile cu clienți plătitori.

## Technical Description

**Pasul 0 — confirmare pe cod (înainte de orice fix):** calea web sincronă
(`src/web/app.py` → `handle_turn`) NU are niciun lock/debounce (verificat: zero ocurențe).
De confirmat cu un test care reproduce: două `handle_turn` concurente pe aceeași conversație →
ce primește AZI clientul al doilea (ipoteza: excepție → 500 sau reply pierdut prin rollback).
Testul devine testul de regresie al fixului.

**Fix 1 — lock per conversație (Redis, scurt):**
```python
# src/redis_bus.py (sau modul nou src/worker/turn_lock.py)
LOCK_KEY = "turnlock:{business_id}:{conversation_id}"   # tenant în cheie (P7)
# acquire: SET key token NX PX <lock_ttl_ms=15000>
# release: DEL doar dacă valoarea == token (compare-and-delete, Lua sau GET+DEL în script)
```
- La `POST /web/chat`: acquire cu așteptare (retry cu backoff scurt) până la
  `turn_lock_wait_max_ms` (config, default 10000).
- Dacă lock-ul NU se obține în timp: **procesăm oricum** + emitem `turn_lock_bypass`
  (principiul 6 — niciodată tăcere; un lock blocat nu are voie să lase clientul fără răspuns).
- TTL-ul (15s) e plasa anti-deadlock dacă procesul moare cu lock-ul luat; release în `finally`.
- Kill-switch: `web_turn_lock_enabled` — **default ON** (e fix de corectitudine, nu feature);
  OFF = comportamentul de azi, byte-identic.

**Fix 2 — conflictul de versiune nu mai omoară reply-ul:**
În `handle_turn`, `patch_conversation_state` se apelează cu `conv["state_version"]` citit la
începutul turului. Cu lock-ul pornit, conflictul devine rar (doar bypass/procese paralele
vechi), dar plasa trebuie să existe:
- prinde `StateVersionConflict` în processor, re-citește `state_version` curent, re-aplică
  patch-ul O SINGURĂ DATĂ (semantica `state_patch` e per-cheie — `active_search`, `safety` —
  last-writer-wins per cheie e acceptabil și azi);
- al doilea eșec: emite `state_conflict_dropped`, loghează (fără PII: doar id-uri) și
  **continuă cu reply-ul** — pierdem patch-ul de stare, nu răspunsul.
- Atenție la ordinea în TX: retry-ul de patch NU trebuie să dubleze insert-urile deja făcute
  în aceeași tranzacție (mesaje/outbox) — retry-ul se face DOAR pe UPDATE-ul de stare.

**Ce NU se schimbă:** pipeline-ul, stagiile, contractul FE. Lock-ul trăiește la margine
(web app + processor), conform separării canal/motor (NX-60).

**TurnContext:** taskul NU adaugă și NU scrie câmpuri noi; `state_patch` rămâne cu ownerii
actuali. Lock-ul e în jurul turului, nu în el.

## Principii CLAUDE.md aplicabile
- **6 (niciodată tăcere):** lock timeout → bypass cu event, NU refuz; conflict dublu → reply
  tot pleacă.
- **7 (business_id pe tot):** cheia de lock include `business_id`; niciun lock cross-tenant.
- **10 (observabilitate din runner):** wait-ul de lock se măsoară la margine, stagiile nu știu.
- **12 (PII):** logurile de conflict conțin doar id-uri de conversație/tur, niciodată corpul
  mesajului.

   (fakeredis + stub DB sau harness-ul `scripts/sim/web_audit.py` local) → documentează în card
   comportamentul real de azi (reply pierdut / 500 / stare coruptă).
2. Implementare `turn_lock` (acquire/release cu token) + config
   (`web_turn_lock_enabled`, `turn_lock_ttl_ms`, `turn_lock_wait_max_ms`) în `src/config.py`.
3. Integrare în calea web (`src/web/app.py`): acquire înainte de `handle_turn`, release în
   `finally`; bypass cu event la timeout.
4. Tratarea `StateVersionConflict` în `src/worker/processor.py`: retry 1× cu re-read, apoi
   drop-patch cu event; reply-ul niciodată sacrificat.
5. Events (`turn_lock_wait_ms`, `turn_lock_bypass`, `state_conflict_retried`,
   `state_conflict_dropped`) prin `ctx.emit`/marginea web.
6. Teste (vezi Test Cases) + `ruff check` + `ruff format --check` + suita completă.
7. Update docs dacă e cazul (docs/SYSTEM-FLOW.md secțiunea web) — bundle în PR.

## Test Cases
**Happy Path**
1. Mesaj unic, lock liber → acquire instant, `turn_lock_wait` neemis, reply normal.
2. Două mesaje concurente → serializare, ambele reply-uri persistă, ordinea stărilor coerentă.

**Edge Cases**
1. Lock ținut peste `wait_max` → bypass + event, reply-ul pleacă.
2. Proces mort cu lock luat → TTL expiră → turul următor nu e blocat permanent.
3. Conversații diferite ale aceluiași business → zero contenție între ele.

**Failure Cases**
1. Redis indisponibil la acquire → tratat ca bypass (event + procesare), NU excepție spre
   client (principiul 6).
2. Conflict de versiune și la retry → patch pierdut cu event, reply livrat, test verifică
   textul răspunsului nealterat.

Toate testele: fakeredis + stub-uri DB/LLM existente — ZERO apeluri reale în CI.
