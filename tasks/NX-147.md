# NX-147 — Dispatcher: concurrency bounded + priority + outbox lag metrics

**Owner:** Claude · **Faza:** P1 · **Track/Wave:** Scalability / Dispatcher · **Branch:** `feat/NX-147-dispatcher-concurrency` · **Complexitate:** M · **Estimare:** 1 zi

## Goal
Ridică throughput-ul și responsivitatea căii de ieșire (audit ARCH-REVIEW-2026-07 §5.11, scor 7.5).
Azi dispatcher-ul procesează **serial** — business-uri unul câte unul, rânduri unul câte unul
(`dispatcher.py:233-241`) — cu poll idle de **2s** (`:245-251`). Un sender lent (Meta/Telegram slow)
crește latența întregii cozi, iar un mesaj de fallback/eroare așteaptă în spatele unui batch de
marketing proactiv. Adaugă: **concurrency bounded** (per tenant + global), **prioritate pe `outbox.kind`**
(răspunsuri user > tranzacțional > marketing proactiv), **idle mai mic / wake pe notify**, și **metrici
de lag** (p50/p95/p99 + dead rate).

## Business Context
La 30+ conversații simultane, o coadă serială cu idle 2s înseamnă că răspunsul unui client poate
aștepta secunde bune după ce a fost generat — exact percepția de „bot lent" care erodează un pilot.
Prioritatea garantează că un fallback de eroare (NX-140) sau un răspuns de user nu stă în spatele unui
val de notificări proactive. Metricile de lag sunt semnalul operațional pentru dimensionare (audit §7,
scalare 100→1000 clienți).

## Technical Description

### Azi (serial)
- `dispatch_due` (`:226`): `for business_id in business_ids: for row in rows: await dispatch_row(...)` — strict serial.
- `run_dispatcher` (`:245`): `idle_sleep=2.0` când nu e nimic de trimis.
- `claim_due` ia `batch=10` per tenant, FIFO pe `next_attempt_at` (fără prioritate de kind).

### Schimbări
1. **Concurrency bounded:** `asyncio.Semaphore` global (ex. 16) + sub-cap per tenant (ex. 4) → rândurile scadente se trimit concurent, dar mărginit (nu inundăm Meta / nu epuizăm pool-ul). `dispatch_row` rămâne pe `tenant_conn` scurt per rând.
2. **Priority queue pe `outbox.kind`:** `claim_due` sortează întâi pe o clasă de prioritate derivată din `kind` (user_reply / transactional=awb,status / proactive_marketing), apoi `next_attempt_at`. Un `ORDER BY priority, next_attempt_at`.
3. **Idle mai mic + wake:** `idle_sleep=0.5` SAU Redis `LISTEN`/pub-sub pe „outbox nou" (Sender publică un semnal la enqueue) → dispatcher-ul se trezește imediat, fără polling agresiv.
4. **Metrici:** emit `outbox_dispatch` cu `lag_ms` (now − created_at) per rând → agregare p50/p95/p99 + `dead_rate` (rânduri `dead`/total). Expus în dashboard (NX-154) + alertă (leagă NX-03).

### Ce NU se schimbă
- Idempotența (idempotency_key UNIQUE) + retry cu backoff — neatinse.
- `dispatch_row` per rând pe `tenant_conn` (izolare + assert) — neatins; doar rulat concurent sub semafor.

## Principii CLAUDE.md aplicabile
- **P5 (un singur punct de ieșire):** rămâne outbox → dispatcher; adăugăm concurență + prioritate, nu o a doua cale.
- **P7:** fiecare `dispatch_row` tot pe `tenant_conn` (business_id) — concurența nu slăbește izolarea.
- **P4:** plafoanele de concurență = explicit în cod (semafoare), nu efect emergent.
- **P6:** prioritatea garantează că fallback-urile de eroare ies primele, nu în spatele marketing-ului.

## Implementation Steps
1. `claim_due` (`src/db/queries/outbox.py`): `ORDER BY <priority(kind)>, next_attempt_at` + eventual coloană/expresie de prioritate.
2. `dispatch_due`: rulează rândurile sub `asyncio.Semaphore` global + dict de semafoare per tenant; `asyncio.gather` mărginit.
3. `run_dispatcher`: `idle_sleep=0.5` (config `dispatcher_idle_sleep_s`) + opțional wake pe Redis pub-sub (`dispatcher_notify_enabled`).
4. Emit `outbox_dispatch` cu `lag_ms`; funcție de agregare pt dashboard.
5. Teste: 3 tenanți × N rânduri → trimise concurent sub cap; un rând `user_reply` scadent bate un `proactive` mai vechi; sender lent nu blochează alt tenant.
