# NX-224 — Ladder top-up: pagina se umple cu potriviri parțiale ETICHETATE, nu rămâne înfometată

**Owner:** Claude (build) / Codex (verify) · **Faza:** Web pilot · **Zi/Ord:** track B, 4 · **Branch:** `feat/NX-224-ladder-topup` · **Complexitate:** M · **Estimare:** 4h
**Model recomandat:** Fable 5 (orchestrare retrieval + interacțiuni cu safety/sesiune/diversificare)

## Goal
Bucla de relaxare se oprește la PRIMA treaptă cu rezultate: `if ranked: break`
([catalog_tools.py:774-779](../src/tools/catalog_tools.py#L774-L779)). O treaptă care
produce 1 produs oprește relaxarea → clientul primește o pagină cu 1 card acolo unde 6
(1 strict + 5 apropiate, etichetate cinstit) ar vinde mai bine. Taskul adaugă top-up: după
treapta câștigătoare, dacă `len(ranked_final) < limit`, coborâm treptele rămase și umplem
DOAR restul paginii cu produse marcate per-produs ca potriviri parțiale.

## Business Context
Exact comportamentul unui vânzător bun: „pe criteriile tale fix am produsul ăsta; îți mai
arăt și 3 apropiate, doar că ies puțin din buget". Pagina plină + onestitate per-produs =
mai multe ocazii de conversie fără nicio minciună de potrivire. La 500+ produse, cazul
„strictul dă 1-2 rezultate" devine frecvent (filtre compuse: categorie+concern+preț).

## Technical Description

**Algoritm (după bucla existentă, înainte de safety gate):**
```python
# NX-224: top-up — strictul întâi, apoi umplere etichetată din treptele rămase.
if topup_on and winning_step is not None and 0 < len(ranked_final) < a.limit:
    have = {str(p["id"]) for p in ranked_final}
    for j in range(relax_depth + 1, len(ladder)):
        lex_j = await search_products_lexical(..., **ladder[j])
        vec_j = await search_products_semantic(...) if query_vec is not None else []
        for p in fuse_candidates(lex_j, vec_j, ...):
            if str(p["id"]) in have:
                continue
            p["partial_match"] = _dropped_constraints(winning_step, ladder[j])
            ranked_final.append(p); have.add(str(p["id"]))
            if len(ranked_final) >= a.limit:
                break
        if len(ranked_final) >= a.limit:
            break
```
- `_dropped_constraints(strict, relaxed)` = diff-ul cheilor care au trecut din valoare în
  `None` între trepte (`["concerns"]`, `["concerns","category"]`...) — sursa disclosure-ului
  per-produs, calculată din ladder, nu ghicită.
- **Ordinea în pagină și în pool: strictele primele, umplutura după** — pool-ul sesiunii
  se seamănă din lista concatenată, deci paginarea continuă natural în zona de umplutură.
- **Safety gate-ul rămâne DUPĂ top-up** (pe uniune) — poziția lui actuală
  ([catalog_tools.py:781-786](../src/tools/catalog_tools.py#L781-L786)) e exact corectă;
  top-up-ul se inserează ÎNAINTE de gate, nu după (niciun produs de umplutură nu ocolește
  contraindicațiile).
- **Diversificarea:** rulează neschimbată pe lista finală; condiția ei `len > limit` o face
  în practică no-op când pagina abia s-a umplut — fără logică nouă.
- **Disclosure spre model:** `_brief` randează pentru produsele cu `partial_match` un marcaj
  scurt („| aproape de criterii: fără concern-ul cerut") — analog `variant_match`
  ([catalog_tools.py:211-212](../src/tools/catalog_tools.py#L211-L212)) — plus nota
  agregată existentă de relaxare ([catalog_tools.py:945-949](../src/tools/catalog_tools.py#L945-L949)),
  extinsă: „primele N respectă toate criteriile; restul sunt apropiate — spune explicit ce
  nu respectă". Modelul NU decide ce e strict/parțial — codul marchează (principiul 2).
- **Interacțiune NX-134 (nu afișa potrivire parțială ca fiind completă):** `partial_match`
  ajunge și în `reason_codes`/warning prin `annotate_reasons` DOAR ca pass-through de flag —
  fără logică nouă acolo.
- **Constrângeri care NU participă la top-up:** brand, `variant_label`, excluderile NX-222 —
  nu sunt în ladder, deci prin construcție nu pot fi „umplute" peste ele. Test explicit.
- **Kill-switch:** `search_topup_enabled`, **default OFF** → byte-identic cu main (disciplina
  flag-urilor; se aprinde după validare pe sim).

**Latență:** în worst-case adaugă (trepte rămase × 2) query-uri DB doar în cazul paginii
înfometate. Paralelizarea lexical+semantic NU intră aici — cele două retrievere împart
aceeași conexiune asyncpg (serializarea per-conexiune e regula NX-219); combinarea într-un
singur SQL (CTE) e follow-up separat, vezi Out of Scope.

**TurnContext:** niciun câmp nou; `partial_match` trăiește pe dict-urile de produs din
`ctx.retrieval` (owner: stagiul de retrieval, neschimbat).
**Cost:** zero LLM nou (embed-ul de query e deja calculat o dată).

## Test Cases
**Happy Path**
1. Filtre compuse, strict 1 + relaxat 8 → pagină 6, ordinea strict-întâi, marcaje corecte.
2. Strict ≥ 6 → zero top-up, `topup_added=0`, comportament identic cu main.

**Edge Cases**
1. Toate treptele sub limit cumulat (strict 1 + relaxat 2) → pagină de 3, fără epuizare
   falsă; „mai arată-mi" → `_NO_MORE_VIEW`.
2. Umplutura conține duplicate cu strictul (același produs pe trepte diferite) → dedup pe id.
3. Safety taie din umplutură sub limit → pagina rămâne cu ce a supraviețuit (fără re-fetch
   în buclă infinită).

**Failure Cases**
1. Retriever-ul semantic aruncă în treapta de top-up → umplutura continuă lexical-only
   (aceeași degradare ca bucla principală).
2. `_dropped_constraints` pe trepte identice → listă goală → produsul NU primește marcaj
   fals de parțial (test).

ZERO LLM real în CI (ScriptedLLM/stub-uri existente).
