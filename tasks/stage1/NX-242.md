## Outcome verificabil

Frontendul are un singur punct de intrare pentru orice payload v2 primit de la backend:
`decodeWebViewV2(unknown)`. Decoderul validează exact JSON Schema publicată de NX-228 și fie întoarce
obiectul valid fără transformări semantice, fie produce o eroare tehnică tipizată. Nu convertește
prețuri, nu inventează defaults, nu repară aliasuri, nu taie/clamp-uiește scoruri și nu decide ce
înseamnă un produs, un status, o comparație sau o acțiune.

Contractul v1 continuă să fie consumat numai de clientul v1 existent. Nu se construiește un adaptor
„magic” v1→v2 în browser.

## Context și findinguri confirmate în frontendul actual

Implementarea curentă din `D:\Work\Sales MVP Frontend Final` amestecă transportul, compatibilitatea și
reguli de domeniu în `src/api/chatClient.js` din repo-ul `Sales MVP Frontend Final`:

- `parsePrice()` transformă stringuri localizate în numere și folosește `0` la input invalid;
- `mapProduct()` introduce defaults (`currency="RON"`), redenumește câmpuri și pierde `variants`;
- `mapComparison()` calculează validitatea lui `winner` și clamp-uiește `confidence`;
- `mapOffer()` decide ce combinații `kind/url/payload` sunt acționabile;
- `normalizeUnderstanding/status/routine/noResults()` repară sau elimină payloaduri;
- `normalizeReply()` acceptă aliasuri precum `no_results`/`noResults` și cade silențios pe colecții goale.

Aceste funcții fac browserul al doilea proprietar al contractului. Un payload backend greșit poate
deveni aparent valid, iar un câmp nou poate fi pierdut fără alarmă. NX-242 înlocuiește clasa aceasta de
cod cu validare structurală strictă și observabilă.

## Boundary frontend pasiv — invariant, nu preferință

### Decoderului îi este permis

- să parseze JSON și să valideze tipuri, enumuri, limite și `additionalProperties`;
- să verifice versiunea/hashul contractului;
- să producă o eroare tehnică low-cardinality, fără payload sau PII;
- să returneze referința validată sau o copie structural identică;
- să permită rendererului să distingă un `block.type` finit, exact cum îl definește schema.

### Decoderului îi este interzis

- `Number(price)`, parsare de monedă sau conversie `"49,90 RON" → 49.9`;
- calcul de discount, total, rating, confidence, stoc, winner, freshness sau eligibilitate CTA;
- defaults comerciale precum `RON`, „În stoc”, „Mai încearcă” ori un URL `/Cart`;
- aliasuri și euristici (`image || image_url`, `url || product_url`, `badge`→`badges`);
- sortare, filtrare, deduplicare ori reordonare de produse/blocuri/acțiuni;
- construirea unui text din numele produsului sau transformarea unui label în comandă;
- fallback conversațional/comercial local;
- logarea payloadului, textului, URL-ului complet, tokenurilor sau mesajelor de validare care le includ.

Validarea structurală și sanitizarea de siguranță nu sunt logică business. Repararea semantică a
datelor este logică business și rămâne backend-owned.

## Decizia de implementare

### Sursa unică de schemă

Nu se rescrie manual schema NX-228 în Zod. Frontendul consumă JSON Schema canonică și generează un
validator JavaScript determinist. Recomandare:

- `ajv` + `ajv-formats` ca **devDependencies**;
- `ajv/dist/2020` în scriptul de generare, strict mode activ;
- `ajv/dist/standalone` pentru validator precompilat;
- runtime-ul widgetului importă validatorul generat, nu întreaga bibliotecă AJV.

Dacă schema NX-228 folosește un draft diferit, Claude adaptează instanța AJV la draftul declarat de
schemă și notează decizia în PR. Nu schimbă schema doar pentru comoditatea frontendului.

Config obligatoriu al validatorului:

```js
{
  strict: true,
  allErrors: false,
  coerceTypes: false,
  useDefaults: false,
  removeAdditional: false,
  validateFormats: true
}
```

`coerceTypes`, `useDefaults` și `removeAdditional` rămân explicit `false`: decoderul observă
contract drift, nu îl ascunde.

### API intern stabil

```js
// input este `unknown`; outputul păstrează exact shape-ul wire.
export function decodeWebViewV2(input, { expectedSchemaHash, onDiagnostic } = {}) {
  // 1. verificare envelope/version;
  // 2. validare generated validator;
  // 3. diagnostic low-cardinality dacă e invalid;
  // 4. return input — fără mapări, defaults, filtrări sau copy local.
}

export class WebViewContractError extends Error {
  // code: unsupported_version | schema_hash_mismatch | invalid_payload
  // issues: numai keyword + instancePath sanitizat/capat; fără value/message raw.
}
```

Nu exporta helpers de produs (`mapProduct`, `parsePrice`) din noul modul. Componentele primesc
ViewModel validat, nu obiecte „normalizate”.

### Artifact și hash

- copia frontend a schemei se generează/copiază printr-un script explicit, nu prin copy/paste;
- scriptul scrie validatorul și hashul așteptat într-o ordine deterministă;
- `npm run chat:contract:check` regenerează într-un director temporar și eșuează dacă rezultatul
  diferă de fișierele versionate;
- scriptul nu face network fetch în CI; artifactul backend se furnizează prin checkout/path sau
  fixture versionată de NX-247;
- un hash greșit nu cade pe v1 și nu încearcă best-effort. Produce `schema_hash_mismatch`.
- compatibilitatea minoră este negociată server-side înaintea livrării payloadului: bootstrapul indică
  un schema hash acceptat de buildul client, iar backendul proiectează numai acel contract;
- un `block.type` absent din schema hash acceptată este `invalid_payload`, chiar dacă backendul îl
  consideră „noncritic”. Rolloutul unui bloc nou cere schema/hash + decoder/renderer compatibile și
  gate-ul de rollout, nu skip în browser.

### Erori și fallback

Decoderul nu compune mesajul pe care îl vede cumpărătorul. El aruncă `WebViewContractError` către
shell-ul tehnic. Până când backendul poate fi contactat din nou, shell-ul poate afișa o singură
propoziție tehnică minimă, constantă și non-comercială (definită în NX-243), fără produse, stoc,
recomandări ori sfaturi. Orice terminal `failed` primit valid de la backend se randează din blocurile
server-owned și are prioritate față de copia tehnică locală.

## Race și failure matrix obligatorie

| Caz | Rezultat obligatoriu | Ce nu este permis |
|---|---|---|
| payload v2 valid | output structural identic | mapare/default/sortare |
| JSON invalid înainte de decoder | transportul produce `invalid_json` tehnic | regex/reparare JSON |
| payload v1 trimis decoderului v2 | `unsupported_version`/`invalid_payload` | fallback automat pe v1 |
| major necunoscut | fail-closed + diagnostic | best-effort render |
| hash contract diferit | `schema_hash_mismatch` | acceptare pentru că shape-ul „pare bun” |
| câmp obligatoriu lipsă | `invalid_payload` | default local |
| tip greșit (`price` object/string neașteptat) | invalid | conversie numerică/string |
| proprietate suplimentară interzisă | invalid | `removeAdditional` |
| URL/format interzis de schemă | invalid | sanitizare care schimbă URL-ul și continuă |
| orice `block.type` necunoscut schemei/hashului acceptat | `invalid_payload`, fără render parțial | skip/omit/delegare best-effort către renderer |
| două decode-uri concurente | pure/reentrant, aceleași rezultate | stare globală mutabilă |
| payload foarte mare | respins de limitele contractului/edge | validare nelimitată care blochează UI |
| eroare AJV | diagnostic fără text/token/value | `console.log(payload)` |

## Test Cases

### Unit/contract

- fiecare fixture valid NX-228 trece;
- outputul este `toEqual(input)` și ordinea arrays rămâne neschimbată;
- `coerceTypes/useDefaults/removeAdditional` sunt dovedite `false` prin teste dedicate;
- v1, unknown version, missing version, bad hash și union action/text invalid pică;
- orice `block.type` necunoscut pică, inclusiv când payloadul conține și un bloc cunoscut randabil;
- toate enumurile vizuale și limitele de text/array/URL sunt testate la `limit-1`, `limit`, `limit+1`;
- erorile nu conțin fragmente sentinel introduse în text, URL și action token;
- scriptul de generare rulat de două ori produce byte-identic;
- validatorul generated corespunde hashului schemei versionate.

### Adversarial

- raw `<script>`, `javascript:`, `data:`, className și SVG în câmpuri nepermise;
- `__proto__`, `constructor`, nesting excesiv și arrays oversized;
- `NaN`, `Infinity`, numere în string, `null` în loc de array;
- acțiune cu `submit` și `navigate` simultan;
- payload valid urmat de mutarea obiectului de către test: decoderul nu păstrează cache global și nu
  contaminează următorul decode.

## Metrici și observabilitate

Decoderul emite numai prin callback/instrumentation seam; NX-246 transportă efectiv evenimentele:

- `web_contract_decode_total{outcome=ok|error,reason,schema_major}`;
- `web_contract_hash_mismatch_total{schema_major}`;
- `web_contract_decode_total{outcome=error,reason=unknown_block,schema_major}`; tipul brut necunoscut nu
  devine label de metrică;
- `web_contract_decode_ms` histogramă.

`reason`, `schema_major` și `block_type` sunt enumuri/capate. Interzis: `conversation_id`, `turn_id`,
URL, text, action token, AJV raw data sau `instancePath` dinamic neallowlisted ca label.

## Rollout și rollback

- NX-242 livrează decoderul și seam-ul, dar nu schimbă implicit clientul activ;
- activarea v2 aparține NX-243/NX-249 și cere endpointurile backend gata;
- v1 și v2 au importuri/entry points separate; nu există runtime auto-detect după shape;
- rollback: buildul anterior/v1 rămâne disponibil; schema/validatorul v2 pot rămâne inert în bundle;
- dacă hashul diferă în canary, oprirea este fail-closed și traficul se întoarce prin mecanismul de
  rollout NX-249, nu prin acceptarea payloadului neverificat.
- schema minoră/blocul nou se livrează numai după negocierea server-side a unui hash acceptat de
  client; nu există fereastră de compatibilitate bazată pe omiterea locală a blocurilor.
