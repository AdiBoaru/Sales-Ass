## Outcome verificabil

`POST /web/v2/turns` acceptă durabil un turn și răspunde rapid, fără să ruleze LLM-ul în request.
Un executor separat revendică exact un turn activ per conversație, îl procesează cu lease și epoch
fencing, persistă ViewModelul terminal prin `TurnCommit`, iar `GET` și opțional SSE recuperează același
rezultat după refresh, pierdere de rețea, moarte de worker sau deploy. Redis poate trezi workerii, dar
Postgres `web_turns` din NX-232 rămâne unica autoritate de corectitudine și recovery.

## Existing state și dovezi reproductibile

- `src/web/app.py:web_chat` rulează `handle_turn(...)` in-process și ține requestul HTTP deschis până
  după pipeline și aftercare.
- `src/web/app.py` folosește lockul Redis NX-221, dar la timeout/Redis indisponibil setează
  `turn_lock_bypass` și procesează totuși; acesta este un guard de performanță, nu single-flight durabil.
- `src/web/app.py:web_message` poate pune evenimente în stream, însă rezultatul merge prin outbox/SSE
  multi-channel și nu are semantics de result replay pe `turn_id`.
- `src/worker/processor.py:handle_turn` poate întoarce `deduped=True` cu `reply=None`; fără ledgerul
  NX-232 retry-ul nu recuperează rezultatul.
- Nu există endpoint autorizat de status/result, lease heartbeat, sweeper de ture abandonate sau
  recovery determinist după restart.

Acest card consumă state machine-ul și tranzacția din NX-232. Nu creează alt tabel de ture și nu
rezervă un număr de migrare. Dacă implementarea NX-232 a schimbat numele serviciilor, Claude adaptează
pointerele după `git fetch` și notează maparea în PR; nu dublează ledgerul.

## Dependencies

- **NX-232:** state machine, accept/idempotency, lease epoch, terminal result și `TurnCommit` sunt
  autoritatea unică; NX-233 nu inventează un al doilea ledger.
- **Transitive NX-228/NX-229/NX-231:** contract v2, auth/result authorization și conn-per-op/admission
  trebuie să existe prin dependența NX-232.
- **Reused:** lockul Redis NX-221 poate rămâne optimization/wakeup temporar, dar nu este correctness gate.
- **Downstream:** NX-239 consumă executorul, NX-241 propagă deadlineul, NX-243 consumă POST/GET/SSE.

## Boundary frontend — nenegociabil

Frontendul generează un `client_turn_id`, trimite textul brut ori `action_token` opac, păstrează
identificatorii tehnici ai turnului și afișează starea/reply-ul primite. Dezactivarea composerului cât
timp turnul este neterminal este UX, nu mutex de corectitudine. Frontendul nu alege workerul, nu
calculează retry/backoff semantic, nu schimbă ID-ul la refresh, nu inventează progres, nu reconstruiește
un răspuns și nu decide dacă un error este sigur de retrimis. Backendul emite toate stările reale,
microcopy-ul de recovery și `composer.enabled`.

## Contract API obligatoriu

### Accept

`POST /web/v2/turns` consumă exact `WebTurnRequestV2` din NX-228 după auth/DLP și produce una dintre:

- `202`: turn nou sau deja activ, cu `turn.id`, `client_turn_id`, status canonic, `status_url`,
  `events_url` opțional și `poll_after_ms` server-owned;
- `200`: același turn deja terminal, cu exact `web-view.v2` persistat;
- `409 idempotency_conflict`: același ID cu fingerprint diferit;
- `409 conversation_turn_in_progress`: alt ID cât timp există un turn activ; payloadul autorizat
  indică turnul activ și cum se recuperează, fără a porni încă unul;
- eroare terminală structurată înainte de accept numai pentru auth/schema/admission; după accept,
  orice rezultat final se citește din ledger.

Requestul HTTP nu cheamă `run_pipeline`, LLM, embedding, tool HTTP sau aftercare.

### Status/result

`GET /web/v2/turns/{turn_id}` reautorizează tenant+sesiune+conversație și întoarce:

- `202` pentru `accepted|working|validating`, cu lifecycle server-owned și fără text comercial parțial;
- `200` pentru `completed|failed|cancelled`, cu ViewModel terminal non-empty byte-equivalent canonic;
- `404/403` indistinguishabil pentru alt tenant/visitor.

`GET /web/v2/turns/{turn_id}/events` este SSE opțional. El transportă numai schimbări reale de status,
heartbeat tehnic rar și rezultatul terminal deja comis. `Last-Event-ID` poate relua streamul; GET rămâne
fallback autoritativ. Este interzis streamingul de tokeni LLM, drafturi nevalidate sau chain-of-thought.

### State machine executor

```text
ledger DB: accepted --claim(epoch+1)--> running --> completed|failed|cancelled
                 ^                       |
                 +--lease expiry/reclaim-+

wire v2:  accepted --> working --> validating --> completed|failed|cancelled
```

- enumul persistent din NX-232 rămâne exact
  `accepted|running|completed|failed|cancelled`; NX-233 nu adaugă `working` sau `validating` ca
  stări DB concurente;
- `working` și `validating` sunt faze/proiecții wire derivate din `status=running` și markerul
  intern curent al executorului; ele nu participă la unique-active/claim/fencing state machine;
- phase markerul este allowlisted și monotonic pentru observabilitate/SSE, dar după reclaim noul owner
  poate relua faza reală fără a crea încă un turn ori încă o stare autoritativă;
- claim/renew/complete sunt compare-and-set pe `business_id`, `turn_id`, status și `lease_epoch`;
- numai ownerul epochului curent poate face heartbeat sau commit;
- expirarea lease-ului permite reclaim bounded, nu două execuții autoritative;
- efectele externe mutabile cer idempotency key/receipt; fencing DB singur nu promite exactly-once
  față de un serviciu extern;
- `deadline_at` nu se prelungește la reclaim;
- un turn e `completed` numai după validarea și commitul atomic al result+message+state+receipts;
- toate terminalele `completed|failed|cancelled` persistă un `web-view.v2` randabil non-empty;
  `cancelled` nu este un status gol și nu obligă frontendul să inventeze recovery copy;
- aftercare rulează după terminal commit, nu ține turnul activ și are retry separat.

## Pași de implementare

1. Citește implementarea efectivă NX-232 și desenează tranzițiile, crash points și ownershipul fiecărei
   coloane. Adaugă characterization tests înainte de refactor.
2. Definește `AcceptedTurn`, `TurnClaim`, `LeaseGuard`, `TerminalCommit` și `TurnStatusView` ca tipuri
   separate; niciunul nu conține raw body, token sau connection.
3. Implementează accept route: auth NX-229 → body cap/DLP NX-230 → admission → `accept_turn` NX-232 →
   commit → wake best-effort. Confirmă că wake-ul nu precedă commitul.
4. Implementează claim batch tenant-safe cu `FOR UPDATE SKIP LOCKED` sau mecanismul ratificat în NX-232.
   Limitează batchul, ordonează fair și nu ține tranzacția în timpul procesării.
5. Rulează pipeline-ul numai după claim; propagă `turn_id`, `lease_epoch`, deadline și cancellation.
   Heartbeatul folosește checkout scurt și se oprește garantat la final/cancel.
6. Marchează `validating` numai când validatorul chiar rulează. Nu emite statusuri cosmetice sau CoT.
7. Leagă completion/failure de `TurnCommit`; dacă epochul este stale, aruncă rezultatul local și nu
   scrie message/state/result.
8. Adaugă sweeperul care re-notifică `accepted`, reclaim-uiește lease expirat și finalizează cu error
   view după attempts/deadline. Folosește advisory lock/leader election dacă există mai multe sweepere.
9. Implementează GET autorizat și SSE ca proiecție a ledgerului. La Redis/pubsub indisponibil, SSE face
   reconnect/poll bounded; nu pierde rezultatul.
10. Mută aftercare după terminal commit într-o coadă/retry separat și dovedește că eșecul lui nu schimbă
    ViewModelul deja persistat.
11. Adaugă shutdown ordonat: stop claims noi, așteaptă bounded, eliberează heartbeat, lasă lease să fie
    reclaim-uit; nu marchează fals completed.
12. Adaugă flags separate pentru accept v2, executor și SSE; v1 rămâne neatins până la NX-249.
13. Rulează fault injection la fiecare crash point și publică în PR numărul pipeline/LLM/tool calls.

## Failure/concurrency matrix

| Caz | Comportament obligatoriu |
|---|---|
| două POST simultane, același ID/request | un rând, un `turn_id`, o execuție |
| același ID după rezultat pierdut | replay exact; zero apel nou de model/tool |
| alt ID cât timp turnul este activ | conflict tipizat + referință autorizată la turnul activ |
| wake Redis pierdut | sweeperul găsește turnul `accepted` din DB |
| Redis complet indisponibil | accept/recovery bounded conform admission; DB rămâne authority |
| worker moare înainte de claim | alt worker revendică turnul acceptat |
| worker moare după claim | lease expiră; epoch nou; deadline original păstrat |
| worker vechi revine după reclaim | heartbeat/commit afectează 0 rows; efectul este respins |
| commit reușește, publish/SSE/HTTP eșuează | GET livrează exact resultul comis |
| SSE se rupe/reia cu `Last-Event-ID` | fără status inventat/dublu result; GET fallback funcțional |
| deadline în tool/LLM/validator | cancel propagat; error ViewModel terminal persistat |
| aftercare moare | resultul rămâne completed; aftercare retry separat |
| request al altui tenant/visitor | 404/403 fără existence leak |
| terminal payload invalid/gol | completion refuzat; safe error ViewModel prin policy P6 |

## Rollout și rollback

1. Deploy schema NX-232 și codul cu executor/accept flags OFF.
2. Pornește recovery în observe-only, apoi executor pe tenant demo fără endpoint public.
3. Activează POST/GET v2 pentru sesiuni interne; SSE separat, deoarece polling este fallback.
4. Canary stable pe `business_id+conversation_id`; un turn acceptat rămâne pe pipeline version capturat.
5. La rollback oprește acceptul nou, dar lasă executorul compatibil să dreneze/terminalizeze turele deja
   acceptate. Nu șterge rows, nu resetează epochuri și nu retrimite ture completed.
6. V1 poate rămâne disponibil pentru trafic nou numai prin NX-249; nu procesează IDs v2 ca mesaje noi.

## Codex Attack Plan

1. Blochează wake-up-ul Redis după DB commit și verifică dacă turnul rămâne blocat fără sweeper.
2. Reclaim-uiește lease-ul, apoi lasă workerul vechi să scrie state/result; orice write reușit este P0.
3. Omoară procesul la fiecare frontieră accept/claim/model/tool/commit/publish și numără execuțiile.
4. Deschide două taburi, trimite ID-uri diferite simultan și verifică ordinea plus single-flight server.
5. Cere resultul cu alt token/visitor și inspectează răspuns/loguri pentru existence/PII leaks.
6. Caută `run_pipeline|handle_turn` în handlerul POST; orice apel sincron este încălcarea outcome-ului.
