## Outcome verificabil

Procesarea unui turn este separată în `resolve/load → compute fără conexiune → commit atomic →
aftercare`. Nicio conexiune tenant nu rămâne checkout-uită peste apel LLM/embedding/HTTP, așteptare
de coadă, retry/backoff sau SSE. Atât ruta web, cât și workerul trec prin admission distribuit cu
limite globale și per-tenant măsurabile.

## Existing state

- `src/web/app.py` deschide `tenant_conn` în jurul `handle_turn`; pipeline-ul și modelul rulează în
  interiorul acelui context.
- poolul are dimensiune mică și poate fi monopolizat de câteva turnuri lente.
- NX-161 a livrat provider/seams parțiale, dar există încă utilizări runtime `deps.conn`.
- admission este process-local și ruta sincronă web nu are aceeași protecție ca workerul.
- dispatcherul/căile externe au același anti-pattern de conexiune peste provider HTTP.

Frontendul nu implementează mutex de corectitudine; dezactivarea butonului este doar UX.

## Scope

### Faza A — load/free layers

- `src/worker/processor.py`, `runner.py`, `context.py`, `aftercare.py`;
- stages gates/language/alias/cache/faq/triage;
- provider DB existent sau `src/db/provider.py` canonic;
- batch load pentru conversation, history, state, facts și config pe checkout scurt.

### Faza B — agent/tools/web

- `src/worker/stages/agent.py`;
- `src/agent/planner.py`, deterministic/finalize/tool executor;
- `src/tools/*.py`: fiecare tool obține o conexiune scurtă prin provider;
- `src/web/app.py`: nu mai pasează conexiune long-lived;
- `src/worker/admission.py`: backend distribuit și per-business cap implicit activ;
- dispatcher/provider calls dacă ating același anti-pattern.

## Out of Scope

- schimbarea semanticii agentului/retrievalului;
- durable turn ledger (NX-232);
- optimizarea fină a latenței (NX-241);
- eliminarea abstrației multi-channel.

## Contract Unit of Work

- `TurnLoadSnapshot`: immutable, safe, fără connection handle;
- `DbProvider.tenant(business_id)`/metode per-op: checkout → query/tx → release;
- `TurnCommit`: singura tranzacție care persistă assistant messages, conversation state version,
  receipts/outbox/result state cerute de cardurile dependente;
- aftercare primește IDs/snapshot safe, nu connection sau obiect mutabil de pipeline;
- o operație de tool care cere mai multe query-uri atomice devine service method cu tranzacție internă,
  nu ține conn între tool calls.

## Pași de implementare

1. Adaugă un checker care listează `deps.conn`, `tenant_conn` peste awaits externe și raw conn în
   runtime; în prima felie rulează report-only.
2. Scrie characterization tests pentru load, optimistic state conflict, retry și commit outbound.
3. Definește snapshoturile și providerul; nu copia obiecte asyncpg în context.
4. Migrează load/gates/free layers, apoi agent/tools în PR-ul aceluiași card numai dacă diff-ul
   rămâne verificabil; altfel livrează două PR-uri legate A/B, fără merge parțial neprotejat.
5. Pentru fiecare tool, grupează query-urile atomice într-o metodă de repository/service.
6. Mută LLM/embed/moderation/media/provider HTTP complet în afara DB context.
7. Mută aftercare după result commit și rulează-l cu provider per-op.
8. Introdu admission distribuit: global cap, per-business cap, fairness și queue-wait deadline.
9. Web v1/v2 folosesc aceeași poartă; nu există bypass silent la dependență indisponibilă.
10. Măsoară pool active/idle-held/wait și publică before/after pe un burst controlat.
11. Transformă checkerul în hard-fail după ce allowlistul runtime ajunge la zero.

## Failure matrix

| Caz | Comportament |
|---|---|
| DB load eșuează | turn terminal/retry policy, conn eliberată |
| LLM timeout | nicio conn ținută; commit fallback separat |
| tool HTTP lent | nicio conn ținută; deadline propagat |
| commit conflict state_version | rebase/retry bounded conform policy, fără rerulare inutilă a acțiunii |
| aftercare eșuează | rezultatul rămâne livrabil; retry async |
| admission store indisponibil | fail-closed/bounded pentru trafic nou, nu cap N×process silent |
| tenant burst | nu blochează ceilalți tenanți |
| cancellation | tranzacțiile deschise rollback și conexiunile se întorc în pool |

## Rollout/rollback

revine la adapterul vechi numai dacă nu reactivează conexiunea peste LLM în production; dacă vechiul
path este unsafe, trafic nou se limitează până la fix, nu se face fail-open.
