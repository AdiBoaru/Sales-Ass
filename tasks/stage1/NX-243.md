## Outcome verificabil

Există exact o instanță WebWidget pe suprafața storefront aprobată. Instanța supraviețuiește
navigării `/store ↔ /product/:id`, trimite textul brut o singură dată cu un `client_turn_id` stabil,
se atașează turnului durabil backend și recuperează rezultatul după timeout, refresh, remount de
rețea sau reconectare. Transcriptul, starea conversației și rezultatul terminal provin numai din
snapshot/result backend; `localStorage` nu mai este o a doua sursă de adevăr.

În timp ce backendul raportează un turn neterminal, clientul nu poate crea alt turn. Garanția de
corectitudine rămâne ledgerul/executorul NX-232/233; guardul frontend este UX și reducere de trafic,
nu lock distribuit.

## Boundary frontend pasiv — ce face și ce nu face controllerul

### Permis

- stări tehnice: bootstrap, submit, accepted, wait, reconnect, recovery, terminal;
- generarea și persistența unui UUID `client_turn_id` înainte de primul POST;
- retry transport cu același ID și backoff bounded;
- memorarea identificatorilor tehnici/session handle/Last-Event-ID;
- decodarea strictă și înlocuirea snapshotului UI cu versiunea server mai nouă;
- dezactivarea controalelor cât timp există un turn activ;
- forward neschimbat pentru text, `action_token`, `id_token`, `context_token`.

### Interzis

- transcript local canonic sau merge semantic între mesajele locale și server;
- append local al unui răspuns assistant, produs, criteriu, progres sau fallback comercial;
- optimistically inventarea unei bule user dacă protocolul backend nu furnizează view-ul acceptat;
- generarea unui nou ID la retry/session renewal/timeout pentru același turn;
- interpretarea acțiunii, contextului, produsului, coșului sau statusului comercial;
- un lock local prezentat ca garanție cross-tab;
- reluarea unui turn vechi într-o conversație cu alt `conversation.id/revision`;
- chain-of-thought/token streaming ori etape fictive cu `setTimeout`.

## Contractul de transport consumat

Numele finale de rute și câmpuri se iau din NX-232/233 OpenAPI. Interfața internă trebuie să fie
însă explicită și injectabilă în teste:

```js
export function createWebTurnTransport({ apiBase, publicToken, fetchImpl, eventSourceFactory }) {
  return {
    bootstrap({ sessionHandle, idToken, contextToken, signal }),
    createTurn({ session, clientTurnId, input, idToken, contextToken, signal }),
    getTurn({ session, turnId, clientTurnId, signal }),
    getConversation({ session, signal }),
    subscribe({ session, afterEventId, onEvent, onDisconnect, signal }),
    renewSession({ session, renewalProof, signal }),
  };
}
```

Reguli:

- `input` este exclusiv `{type:"text", text}` sau `{type:"action", action_token}`;
- transportul nu inspectează `action_token` și nu transformă labelul în text;
- fiecare JSON v2 trece imediat prin `decodeWebViewV2` înainte de state/UI;
- `renewalProof` rămâne opac și răspunsul de renewal este folosit numai dacă NX-229 confirmă
  `continuity_preserved`; clientul nu deduce lineage din IDs ori claims;
- identity/context tokens se forwardează în locul stabilit de NX-229/NX-234; nu se decodează și nu
  se persistă dacă sunt short-lived/secrete;
- EventSource nu suportă headers arbitrare: nu inventa un workaround cu token în URL dacă NX-229 nu
  îl autorizează. Folosește exact mecanismul semnat server-side sau fetch-stream stabilit acolo;
- SSE transmite numai stări operaționale/result atomic. Polling este fallback, nu al doilea rezultat.

## State machine tehnică obligatorie

Nu este necesară o bibliotecă nouă. `useReducer` + efecte izolate sunt preferate unei colecții de
booleeni. Dacă Claude propune XState, trebuie să demonstreze necesitatea, bundle delta și să obțină
accept explicit; altfel rămâne în afara scope-ului.

```text
uninitialized
  └─ BOOTSTRAP → bootstrapping
bootstrapping
  ├─ snapshot fără active turn → ready
  ├─ snapshot cu active turn → waiting
  └─ transport/contract fatal → unavailable
ready
  ├─ SUBMIT (ID persistat înainte de I/O) → submitting
  └─ SERVER_ACTIVE_TURN → waiting
submitting
  ├─ accepted/existing → waiting
  ├─ outcome necunoscut (timeout/offline) → recovering
  └─ reject terminal valid → ready după aplicarea ViewModelului failed
waiting
  ├─ progress valid → waiting
  ├─ SSE disconnect/timeout → recovering
  └─ completed|failed|cancelled valid → ready
recovering
  ├─ GET găsește accepted/working → waiting
  ├─ GET găsește terminal → ready
  ├─ session_expired + renewal proof → renewing
  │    ├─ continuity_preserved (same actor/session_family) → recovering same conversation/turn
  │    └─ proof/family invalid ori revoked → fresh_bootstrap → ready cu conversație nouă
  └─ budget server epuizat → unavailable/retry UI tehnic, fără turn nou
```

Invariante reducer:

1. maximum un `activeTurn` per controller;
2. `ready` este singura stare care poate iniția un turn nou;
3. `clientTurnId` nu se schimbă dinaintea POST-ului până la status terminal;
4. o revizie/snapshot mai veche nu înlocuiește una mai nouă;
5. un rezultat cu alt `conversation.id`, `turn.id` sau `client_turn_id` este respins și raportat;
6. unlockul vine numai din status terminal valid ori reject dovedit înainte de accept;
7. close/navigare nu anulează logic turnul server; doar conexiunea UI poate fi oprită și recuperată.

## Persistență locală permisă

Se înlocuiește `aria-chat-messages` cu un record tehnic versionat și namespaced pe integrare/origin,
de exemplu:

```json
{
  "storage_version": 2,
  "session_handle": "opaque",
  "conversation_id": "opaque",
  "active_turn_id": "opaque-or-null",
  "client_turn_id": "uuid-or-null",
  "last_event_id": "opaque-or-null"
}
```

- Nu persistă `messages`, `blocks`, textul userului, products, actions, id_token sau context snapshot.
- Dacă NX-229 marchează vreun handle ca non-persistabil, se respectă acea regulă și bootstrapul
  server recuperează prin mecanismul aprobat.
- Proof-ul/handle-ul de renewal rămâne opac. Frontendul nu citește, construiește ori compară
  `actor_id`/`session_family`; acceptă continuitatea numai din outcome-ul semnat/autorizat NX-229.
- Record invalid/vechi este ignorat și înlocuit prin bootstrap, fără migrare semantică.
- `localStorage`/BroadcastChannel exceptions (private mode/quota) nu rup widgetul.

## Politica de submit, timeout și recovery

1. La submit valid, controllerul generează UUID, îl scrie în storage și setează guardul sincron
   **înainte** de primul `await`.
2. Toate controalele creatoare de turn primesc imediat busy/disabled prin state machine.
3. POST-ul folosește un timeout de transport configurabil conform NX-233. Timeoutul înseamnă
   „outcome necunoscut”, nu „turn eșuat”.
4. La outcome necunoscut, controllerul caută după același `client_turn_id`; nu face un POST nou cu ID
   nou și nu deblochează composerul.
5. Retry de POST este permis numai dacă protocolul NX-232 îl cere și numai cu același ID/body.
6. SSE reconnect folosește event cursor; eventurile duplicate sunt deduplicate după ID/revision.
7. Poll fallback are exponential backoff + jitter + plafon și respectă `Retry-After`.
8. Numai eroarea tipizată `session_expired` pornește renewalul NX-229. Clientul trimite proof-ul opac;
   dacă serverul confirmă același actor + `session_family`, înlocuiește handle-ul și reia lookupul
   aceleiași conversații/turn. Un 401/403 generic, revocarea sau family mismatch nu sunt retry semantic.
9. Fără proof valid, clientul nu trimite vechiul `conversation_id` sub noua sesiune. Curăță atomic
   recordul tehnic vechi, aplică outcome-ul/UI state explicit `new_session` din bootstrap și pornește
   o conversație nouă. Nu păstrează bule locale și nu simulează restaurarea istoricului.
10. La 409/existing active turn, se atașează turnului indicat de server. Nu compune mesaj local.
11. La status terminal, aplică ViewModelul complet, curăță active IDs atomic și abia apoi permite un
    nou submit.

## Cross-tab

`BroadcastChannel` poate transmite numai invalidări tehnice (`turn_started`, `snapshot_stale`,
`turn_terminal`) fără text/payload. La primire, tabul cere snapshotul backend. Nu acceptă ViewModelul
altui tab ca adevăr și nu implementează lease în localStorage.

Dacă două taburi trimit în aceeași milisecundă, NX-232/233 decide turnul acceptat/existent; ambele
taburi converg apoi pe snapshot. Acesta este test obligatoriu în NX-247.

## Race și failure matrix obligatorie

| Scenariu | Stare/rezultat obligatoriu | Invariant verificat |
|---|---|---|
| dublu click sincron | un singur `createTurn` | guard înainte de `await` |
| Enter + click în același tick | un singur POST | aceeași cale de submit |
| POST 202, răspuns pierdut | `recovering`, lookup același ID | zero turn nou |
| timeout înainte să știm dacă a ajuns | lookup/retry same ID | idempotency |
| refresh în `working` | bootstrap vede active turn, reatașare | transcript server-owned |
| route Store→Product în `working` | widget nu se remontează | singleton |
| SSE duplicate/out-of-order | ignoră event vechi, refetch la gap | revision monotonic |
| SSE cade | polling bounded/reconnect | fără unlock prematur |
| `session_expired` + proof valid în wait | rotate handle; server confirmă same actor/family; lookup same turn | continuitate autorizată |
| expirare fără proof / proof invalid / family mismatch | bootstrap `new_session`, clear tehnic atomic, UI explicit fără transcript vechi | zero history split-brain |
| 401/403 non-renewable | unauthorized/unavailable conform contractului | fără loop de renew și fără lookup cu sesiune nouă |
| 409 active turn | attach la server turn | backend authority |
| 429 înainte de accept | aplică error ViewModel/retry-after | fără assistant copy local |
| 5xx/outcome necunoscut | recovery, nu ID nou | no duplicate spend |
| două taburi simultan | converg la server snapshot | fără local lock ca adevăr |
| tab A terminal, tab B offline | B recuperează la reconnect | result replay |
| New chat apăsat în wait | control inactiv | fără stale reply attach |
| result cu alt conversation/turn | respins + refetch/diagnostic | correlation |
| storage corupt/indisponibil | bootstrap clean, funcțional | graceful technical degrade |
| contract invalid | unavailable tehnic | zero render best-effort |

## Test Cases

### Happy path

1. Bootstrap fără conversație activă → snapshot valid → `ready`.
2. Submit text → UUID persistat → un POST → `accepted/working` → result `completed` → snapshot afișat
   și composer reactivat.
3. Acțiune opacă (fixture, feature off până la NX-236) traversează transportul byte-identic.
4. Store→Product→Store păstrează aceeași instanță, open state și controller.

### Concurrency/recovery

- toate rândurile din matricea de mai sus au teste deterministe cu fake timers/fetch/SSE;
- testul double-submit numără apelurile, IDs și body-urile;
- testul response-loss dovedește că backendul mock a acceptat, iar UI recuperează fără al doilea
  execution ID;
- testul refresh pornește un controller nou numai din storage + server snapshot, nu din transcript;
- testul cross-tab livrează invalidări, apoi ambele taburi fac refetch și ajung la aceeași revision.
- renewal cu proof valid rotește handle-ul, păstrează `client_turn_id`/turnul și reia lookupul numai după
  `continuity_preserved`; proof absent/corupt/revocat/family mismatch produce `new_session`, șterge
  corelația veche și nu cere vechiul `conversation_id`.

### Security/privacy

- id/context/action tokens nu apar în localStorage nepermis, console, error text sau metric labels;
- un event/result cu correlation diferit nu este randat;
- un response de renewal care declară alt actor/family ori nu are dovada autorizată nu poate restaura
  conversația; 401/403 generic nu intră într-un loop de renewal;
- URL-urile requestului sunt construite din API base/config allowlisted, nu din payload arbitrar;
- cleanup închide EventSource/AbortController/listeners și nu mai face setState după unmount.
