## Outcome verificabil

Orice request/result/action WebWidget este legat criptografic și prin autorizare DB de tenantul,
sesiunea, visitorul și conversația corecte. `business_id` nu vine niciodată din browser. Există o
singură regulă documentată pentru `id_token`; CORS permite exact originurile reale și nu este tratat
ca mecanism de autentificare.

## Existing state

- `src/web/app.py` acceptă `id_token` în body și îl verifică opțional.
- Frontendul local curent trimite Supabase JWT în `Authorization`, dar body-ul nu conține
  `id_token`; backendul nu folosește acel header pentru shopper identity.
- `src/webhook/app.py:177-181` permite CORS headers `Content-Type` și `Last-Event-ID`, nu
  `Authorization`.
- proxy-ul dev folosește `shop.nativxtech.com`, în timp ce demo/deploy indică și
  `demo.nativxtech.com`.
- tokenul public din bundle identifică integrarea, dar nu poate fi secret de protecție a costului.

## Boundary frontend — nenegociabil

Frontendul doar forwardează tokenurile primite de la host și identificatorii tehnici. Nu validează
identitatea, nu derivă tenantul, nu decide dacă un user poate vedea o comandă și nu păstrează
secrete. Un public widget token rămâne public.

## Modelul de încredere obligatoriu

1. `widget_public_token` → rezolvă server-side canalul și `business_id`; nu autorizează date private.
2. `visitor_id + session_sig` → sesiune anonimă cu `iat`, `exp`, `key_id`, origin binding și rotație.
3. `id_token` host-signed opțional → identitate shopper stabilă; frontendul îl forwardează în body.
4. Demo/site access token → control de acces la site/reverse proxy; nu devine automat customer ID.
5. `turn_id`/`action_token` → autorizate din nou pentru aceeași sesiune/conversație/tenant.

Nu păstra două transporturi ambigue pentru același credential. Pentru v2, identity canonic este
`id_token` din contract. Dacă infrastructura demo cere `Authorization`, headerul este validat
explicit ca access gate sau consumat la edge; nu este ignorat și nu este reinterpretat ca shopper.

- login UI/Supabase Auth în frontend;

## Pași de implementare

1. Documentează threat model: token public furat, origin spoof, token expirat, session fixation,
   visitor swap, turn enumeration, action replay, tenant collision și key rotation.
2. Extinde versiunea sesiunii fără a rupe v1. Semnează claims canonice: channel/public-token ref,
   visitor, `iat`, `exp`, `key_id`; include origin normalizat dacă policy o cere.
3. Implementează rotație dual-key: key curentă semnează, curentă+precedentă verifică în overlap.
4. Rezolvă originurile per channel/business; `Origin` este policy/admission, nu dovadă de identitate.
5. Standardizează `id_token`: algoritm fix, issuer/audience dacă există, `exp/sub` obligatorii,
   degradare anonimă pentru feature-uri publice, dar fail-closed pentru date private.
6. Leagă orice lookup viitor de turn/result de session principal, nu doar de un UUID greu de ghicit.
7. Decide și testează CORS pentru originurile reale. Nu folosi wildcard cu credentials.
8. Redactează complet tokens/claims din logs și exceptions; events conțin doar reason code.
9. Adaugă rate limits pe bootstrap, turn și result polling per tenant+visitor/IP bucket, fără PII în key.
10. Documentează integrarea host: cine emite identity tokenul, TTL, refresh și logout/revocation.

## Failure matrix

| Caz | Comportament |
|---|---|
| public token necunoscut/revocat | 401/403 tipizat, zero lookup tenant data |
| origin nepermis | request respins înainte de pipeline |
| sesiune expirată | bootstrap nou; transcript server restore explicit, nu split-brain silent |
| signature/key_id invalid | fail-closed; tokenul nu apare în log |
| identity token absent | chat public anonim; features private rămân blocate |
| identity token expirat/greșit | anonim pentru shopping public; error view pentru operație privată |
| alt visitor cere un turn | 404/403 indistinguishabil, fără leak de existență |
| rotație în overlap | sesiunea veche rămâne validă până la expirare |
| Redis/cache indisponibil | secret/config lookup bounded; fără bypass de autorizare |

## Rollout/rollback

Feature flag separat pentru session-v2 verification. În overlap se acceptă v1 și v2, dar numai v2
poate accesa endpointurile `/web/v2/*`. Rollback read-only la v1 nu invalidează turele v2 persistate;
acestea rămân recuperabile după reactivare.

## Codex Attack Plan

1. Refolosește sesiunea cu alt public token și alt origin.
2. Trimite `Authorization` valid, dar fără `id_token`; verifică să nu creeze identity implicită.
3. Încearcă să citești un `turn_id` al altui visitor/tenant.
4. Simulează key rotation la mijlocul unui turn și verifică recovery fără bypass.
