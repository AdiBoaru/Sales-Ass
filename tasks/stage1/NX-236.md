## Outcome verificabil

Orice control semantic din WebWidget este creat de backend ca acțiune allowlisted și livrat printr-un
`action_token` opac, cu integritate, expiry, key rotation și binding la tenant+sesiune+conversație+
source turn+state revision. Browserul retransmite tokenul neschimbat; backendul îl verifică, rezolvă
referințele și execută comanda printr-un kernel determinist sau o transformă într-un input structurat
pentru brain. Retry-ul aceluiași turn replayează rezultatul, iar replay-ul intenționat cu alt turn nu
repetă o mutație. Labels nu sunt niciodată parsate ca mesaje sau business commands.

## Existing state și dovezi reproductibile

- `src/channels/web/render.py` transformă `rich.chips` în strings; `Chip.payload` se pierde pe calea v1.
- `src/agent/deterministic.py:_review_choice_chips` și alte next steps produc etichete, iar frontendul ar
  trebui să retrimită textul pentru a reconstrui intenția.
- `src/models.py:Chip` are label/payload, dar payloadul nu are un contract crypto, expiry, audience,
  source revision sau one-shot semantics.
- NX-219/NX-220 au îmbunătățit canonicalizarea și review follow-up, dar sunt text-driven și nu acoperă
  tampering/replay/cross-tenant.
- NX-232 poate lega `action_id` de turn/ledger; cardul curent trebuie să consume acea seam, nu să creeze
  idempotency paralel în Redis.

## Dependencies

- **NX-228:** unionul finit `ActionView`/`activation.submit` și requestul `input.type=action` sunt stabile.
- **NX-232:** accept/fingerprint/result ledger și `action_id`/source action seam sunt autoritatea replay.
- **NX-235:** refs, state revision și reference precedence sunt canonice.
- **Reused:** NX-219 canonicalization și NX-220 review/deixis; se apelează prin kernel, nu se clonează.
- **Downstream:** NX-237 înregistrează mutation receipts; NX-240 proiectează labels/actions display-ready.

## Boundary frontend — nenegociabil

Frontendul afișează `label`, `appearance`, `icon` și retransmite exact tokenul de la
`activation.type=submit`. Nu decodează Base64/JWE/JWS, nu citește `kind`, nu construiește payload JSON,
nu mapează label→mesaj, nu înlocuiește product/variant IDs, nu decide dacă action este mutabilă și nu
face optimistic cart mutation. Pentru `navigate`, deschide numai `href/target` deja validate conform
contractului. Orice text de expired/stale/already-used vine în ViewModel de la backend.

## Contract action obligatoriu

### Separarea dintre view și command

- `ActionView`: `{id,label,appearance,icon?,activation}` — display-only, validat de NX-228;
- `ActionEnvelope`: server-only `{action_id,kind,args,policy,audience,source,expires_at,key_id}`;
- `ActionCommand`: rezultatul typed după crypto+auth+state validation;
- `ActionOutcome`: `handled(result/state proposal/receipt ref)|continue(brain input)|rejected(error view)`.

Tokenul trebuie să fie opac în sens practic. Preferința Stage 1 este un envelope AEAD/sealed sau un
handle aleator+MAC, nu claims comerciale Base64 lizibile. Tokenul nu conține raw message, PII, nume,
preț, stoc, URL ori business name. Claims/binding minime:

- versiune, `key_id`, `action_id`, issued/expiry;
- audience `web-widget-v2`;
- refs criptografice/pseudonime pentru `business_id`, session, conversation, source `turn_id`;
- source conversation/state/display revision;
- kind allowlisted și args canonice bounded (refs, quantity, filter enum), niciodată free-form prompt;
- consumption policy.

Semnătura nu înlocuiește autorizarea DB: după decode, backendul compară sesiunea curentă, tenantul,
conversation/source turn, revizia și faptul că action a fost efectiv emisă în ViewModelul terminal.

### Registry Stage 1

- non-mutating: `select_product`, `request_details`, `request_reviews`, `compare_products`,
  `refine_search`, `show_more`, `answer_clarification`, `dismiss_notice` dacă are efect server-side;
- commerce după NX-237: `cart_add`, `cart_set_quantity`, `cart_remove`, `cart_clear`, `checkout`;
- `navigate` nu devine submit token dacă este doar link; backendul livrează URL validat direct;
- orice kind necunoscut este respins; nu există `execute_tool`, `run_prompt`, raw route sau code action.

Toate submit actions sunt one-shot implicit. Retry cu același `client_turn_id` folosește ledger replay.
Dacă un kind sigur trebuie repeatable, policy-ul se allowlistează explicit și fiecare activare are un
nou target turn/idempotency record; nu se face bypass generic.

### Migrare

Default fără migrare: se folosește `action_id`/source seam din ledgerul NX-232 și envelope sealed.
Dacă implementarea reală NX-232 nu poate dovedi emission+consumption atomic, se oprește cardul și se
propune o extensie cu **următorul număr liber după fetch și după ledger**, coordonată în registrul Stage 1.
Nu se hardcodează `039`, nu se folosește Redis-only și nu se creează un action table fără retenție/RLS.

## Pași de implementare

1. Inventariază CTA/chips v1 și creează matricea `source → kind → args → mutability → handler → receipt →
   stale policy`. Elimină/omite orice acțiune fără handler sigur.
2. Definește enums/models bounded și dispatch exhaustiv. Un action kind nu este string passthrough spre
   tools, routes, SQL sau prompt.
3. Alege primitive crypto dintr-o bibliotecă auditată deja disponibilă sau adaugă o dependență minimă
   pin-uită. Nu implementa criptografie custom. Documentează threat modelul și formatul versionat.
4. Implementează key ring cu `current` pentru issue și `current+previous` pentru verify în overlap;
   unknown key/alg/version fail-closed, fără token în exception/log.
5. Implementează issue numai după ce resultul și action envelope sunt validate. Bind source turn,
   conversation/state/display revision și expiry; persistă dovada emission în tranzacția terminală.
6. În ingress action: auth NX-229 → size/schema → crypto open → audience/expiry/session/tenant/source
   verify → state/reference freshness → atomic ledger accept+consume.
7. Integrează kernelul înainte de triage. Acțiunile exacte pot răspunde determinist; cele de refinement
   produc input structurat pentru brain, fără a fabrica text de user.
8. Leagă clarification actions de question/options IDs; alegerea stale nu modifică stateul.
9. Adaugă cart handlers ca `unavailable` până la NX-237. Nu confirma add/remove/checkout fără receipt.
10. Păstrează `navigate` separat și validează HTTPS/relative allowlist la emitere; nu semna URL client-supplied.
11. Adaugă redactare: tokenul și claims nu apar în logs/traces/analytics/ledger fingerprint.
12. Testează rotație, expiry, tamper, replay, source deletion/retention și rollback v1/v2.

## Failure matrix

| Caz | Comportament obligatoriu |
|---|---|
| un bit schimbat în token | reject generic, zero handler/model/tool |
| token valid sub alt tenant/session | 404/403 generic; zero existence leak |
| token expirat | terminal error view cu retry/new-action policy server-owned |
| `key_id` vechi în overlap | valid până la expiry; key necunoscut fail-closed |
| source turn/result absent sau action neemisă | reject, chiar dacă crypto este valid |
| source state/display revision stale | stale error/re-resolution explicit; nu primul produs |
| același token + același client turn ID | exact result replay, zero a doua execuție |
| același token + alt client turn ID | `action_already_consumed`, fără side effect |
| două consumări concurente | una câștigă atomic; cealaltă primește outcome canonic |
| kind/args necunoscute ori oversized | reject înainte de dispatch |
| action `cart_add` înainte de NX-237 | CTA omis la emitere sau unavailable onest; fără confirmare |
| handler timeout | terminal error/retry policy; consumption/receipt consistent |
| frontend schimbă labelul | semantica nu se schimbă; labelul nu este input |

## Manual drive obligatoriu

Emite un ViewModel cu review, compare, clarify și un cart action disabled. Pentru fiecare token: execută
valid, editează un byte, schimbă sesiunea/tenantul, expiră timpul, schimbă state revision și trimite de
două ori concurent. Contorizează handler/model/tool/mutation. Apoi rotește cheia între issue și consume.
PR-ul conține comanda/harnessul, outcome codes și counts redacted; tokenurile complete nu apar.

Nu pune action/turn/product/session/business IDs, token hash complet sau args în labels. Alarme pe tamper
spike, unknown key, stale rate, double-consume și mutation fără receipt (după NX-237).

## Rollout și rollback

Issue shadow poate crea tokens nelivrate pentru validare crypto. Activează apoi numai action kinds
non-mutating pe tenant demo; cart kinds rămân omise până la NX-237. Key overlap precede deployul; rollback
păstrează verifierul cheii precedente până expiră toate tokenurile emise. Dezactivarea issue nu invalidează
imediat actions deja afișate: fie verifierul rămâne read-compatible, fie backendul întoarce error view
onest. V1 label-as-message nu este extins și se elimină doar la cutover NX-249.

## Codex Attack Plan

1. Mută tokenul între tenant, visitor, conversație și source turn; caută orice handler apelat.
2. Consumă concurent același token cu două `client_turn_id`; orice dublu side effect este P0.
3. Editează kind/args/key/version/expiry și încearcă alg confusion/oversized token.
4. Reordonează produsele după emitere și execută ordinal/action stale; nu trebuie să aleagă alt produs.
5. Caută parsing `label|suggestion` în frontend/backend ingress și passthrough action→tool.
6. Caută tokenul sintetic în DB/log/trace/error; apariția lui completă este finding critic.
