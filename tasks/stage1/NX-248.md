## Outcome verificabil

Același artefact container testat este promovat prin staging în producție după digest, nu reconstruit
și nu tras prin tagul mutabil `latest`. Deployul are preflight, migrare separată, startup/readiness,
smoke WebWidget v2, evidence packet, aprobări și rollback la digestul anterior. Niciun runtime process
nu primește credentiale admin pentru DB și niciun secret nu intră în imagine, git, process args,
logs sau artifacts.

Imaginea este non-root și minimă, dependențele sunt hash-locked, acțiunile CI sunt pin-uite, iar
release-ul produce SBOM, scan, provenance și semnătură verificabilă. Există un runbook DR testat pe un
restore izolat, cu surse de adevăr, RPO/RTO, Redis-loss recovery și dovada că un turn acceptat nu se
pierde. Readiness verifică semantic că instanța poate servi v2; un socket deschis nu mai este „healthy”.

## Existing state și risc demonstrabil

- `.github/workflows/deploy.yml` construiește la push și publică `latest` + SHA, apoi face SSH și
  `git pull && docker compose pull && up -d`; production compose consumă `:latest`, deci artefactul
  efectiv nu este pin-uit/reproductibil și rollbackul nu este o operație declarată.
- Workflowul folosește actions prin tag major, nu commit SHA, iar deployul curent nu generează/verifică
  SBOM, provenance, semnătură sau vulnerability report.
- SSH rulează prin userul configurat și folosește o secvență care include opțiuni permissive; nu există
  environment approval, host-key trust pin-uit și least-privilege deploy account demonstrate.
- Webhook healthcheckul din `docker-compose.prod.yml` verifică doar dacă portul 8000 acceptă socket.
  Workerul nu are readiness semantică, iar config/schema/DB/ledger pot fi nefuncționale cu container
  aparent „healthy”.
- Aplicația și migrarea împart astăzi imaginea/boot seams; fără un job de migrare separat există riscul
  de race, credential admin în runtime sau restart-loop după un DDL incompatibil.
- Containerul este deja non-root și Redis nu publică portul — acestea se păstrează — dar compose nu
  impune încă `read_only`, cap drop, no-new-privileges, PID/CPU limits și tmpfs explicit.
- Redis are AOF și volum, însă nu există un document as-built care spune ce este autoritativ după
  NX-232/233 și cum se recuperează accepturile dacă volumul Redis dispare.
- Nu există dovadă periodică de restore Postgres/PITR și nici targete RPO/RTO condiționate de
  capabilitățile reale ale providerului.

## Boundary frontend — nenegociabil

Nu există modificări în `Sales MVP Frontend Final`. Frontendul nu alege release, endpoint de failover,
retry policy, health state, secret, tenant, feature flag sau fallback comercial. El continuă să
trimită raw text/action token opac și să afișeze envelope-ul serverului. Orice mesaj de degradare,
maintenance, retry sau recovery este un ViewModel backend-owned și durabil conform NX-228/232.

Browserul nu interoghează un dashboard intern, nu decide că „health=degraded” este totuși sigur și
nu trece la v1 pe cont propriu. Routingul/cutoverul sunt server-side în NX-249.

## Arhitectura de release obligatorie

```text
commit SHA
  → CI gates + DB/container integration
  → build o singură dată
  → image digest + SBOM + provenance + signature + scan report
  → deploy staging al aceluiași digest
  → migration preflight/job + readiness + Web v2 smoke + failure probes
  → evidence packet + approval production
  → verify signature/digest pe host
  → backup/PITR precondition + migration job
  → deploy services + readiness + smoke
  → NX-249 canary; apoi promotion sau rollback la previous digest
```

Tagurile (`sha-*`, versiune semantică) sunt numai pointeri pentru oameni; manifestul și compose
folosesc `image@sha256:...`. Nu se face build și nu se execută `git pull` pe VPS în hot path.
Deploy manifestul conține release SHA, image digest, schema compatibility range, config revision,
OTel resource version, timestamp și previous digest.

## Health/readiness contract

### Endpointuri API

- `GET /health/live`: procesul/event loop răspunde; fără DB/Redis/model call. Nu dezvăluie secrete,
  hostnames sau stack trace.
- `GET /health/startup`: config obligatoriu valid, schema DB în compatibility range, registry/policy
  load valid, token keys prezente și build manifest coerent. Eșecul oprește traficul.
- `GET /health/ready`: probe bounded pentru dependențele declarate **required** de NX-233, pool DB
  runtime cu rol corect, ledger read/write capability prin tranzacție rollback/dry check, executor
  capacity și migration compatibility. Dependențele optional/degraded sunt listate prin reason code
  intern, nu transformate arbitrar în required.

Răspunsul public este minimal: status, release, schema compatibility și timestamp. Detaliile per
dependency sunt accesibile numai pe network/operator path autorizat și tot fără DSN/tenant/token.
Nicio probă nu apelează LLM, nu creează conversație și nu ține conexiunea peste deadline.

### Procese non-HTTP

Worker/executor și scheduler expun un health command/heartbeat structurat cu `last_success`,
`lease_loop_alive`, `schema_compatible`, `queue_lag_bucket` și release SHA. Un fișier heartbeat scris
de un process mort nu este suficient: probele verifică freshness, PID/process lifecycle și capacitatea
de a obține bounded următorul lease fără a muta un turn real.

Docker folosește start periods și retries distincte pentru startup versus readiness. Reverse proxy
trimite trafic numai după ready; liveness nu repornește un proces doar pentru că Postgres are o
întrerupere temporară.

## Secrete și acces

Inventarul minim: DB runtime, DB migration/admin, Redis, OpenAI runtime, session/action signing keys,
OTLP credentials, GHCR pull, SSH deploy și orice TLS/DNS credential.

- Runtime primește numai secretul necesar rolului său; workerul folosește `bot_runtime`, iar
  credentialul de migrare există exclusiv în jobul pre-deploy, cu TTL/rotație dacă providerul permite.
- Secretele nu sunt `ARG`/`ENV` în Dockerfile, image layers, compose committed, command line, labels,
  health response, `docker inspect`-visible plaintext, logs ori artifacts.
- Pentru VPS/Compose, secret delivery folosește fișiere montate read-only cu owner/mode minim și
  suport `_FILE` în config sau un secret manager aprobat. Un `.env` root-readable poate rămâne numai
  ca tranziție documentată cu owner și deadline; nu este declarat target final.
- Deploy account nu este root, nu are shell/permisiuni generale și poate opera doar directorul/proiectul
  Nativx și pull/restart/inspect necesar. Host-key checking este strict cu fingerprint pin-uit.
- Cheile de session/action suportă current+previous și `key_id`; rotația nu invalidează brutal
  turnurile active. DB/Redis/OpenAI/OTLP/SSH au runbook separat de rotație și revocare.
- Un secret scan rulează pe git history relevant, build context, image history și artifacts.

## Supply-chain și container hardening

### Build/release

- pin GitHub Actions la commit SHA, cu comentariu de versiune pentru mentenanță;
- `permissions` default `{}` și capabilități minime per job; OIDC numai unde este necesar;
- generează lock runtime complet cu hashes și instalează cu hash verification; top-level version pin
  singur nu este lock pentru dependențele tranzitive;
- pin base image prin digest și păstrează proces automat/reviewed de update;
- build reproducibil din context minim `.dockerignore`, fără `.git`, `.env`, tests cu secrete sau docs
  private; păstrează numai SQL/migration runner necesar jobului dedicat;
- buildx produce SBOM SPDX/CycloneDX și provenance; image este semnată keyless/approved și verificată
  pe deploy pentru repo, workflow identity și digest;
- rulează vulnerability scan OS+Python, `pip-audit` și secret scan. Critical/high necunoscut blochează;
  excepțiile cer CVE, justificare, owner și expirare, nu `continue-on-error` generic.

### Runtime

- user non-root cu UID/GID explicit și fișiere app neinscriptibile;
- `read_only`, `tmpfs` bounded unde aplicația chiar scrie, `cap_drop: [ALL]`,
  `no-new-privileges`, PID/CPU/memory limits și log rotation;
- signal handling și shutdown grace permit lease release/fencing, OTel bounded flush și niciun turn
  marcat complet înainte de commit;
- numai API este pe networkul Traefik; DB/Redis/OTLP nu publică porturi; firewallul VPS expune doar
  administrarea aprobată și 80/443 după politica reală;
- imaginea nu include compiler/cache/package manager artifacts inutile în runtime.

## Migrare și compatibilitate

1. CI verifică migrations pe Postgres 16 efemer, de la schema snapshot și de la ultima versiune.
2. Preflight rulează `scripts/migrate.py --check`, verifică lock/advisory policy și compatibility range.
3. Backup/PITR precondition este confirmat înaintea unei migrări producție.
4. Un job unic cu credential admin aplică migrarea; serviciile runtime nu auto-aplică concurent.
5. DDL este expand/contract: noua și precedenta imagine rulează simultan/în rollback pe schema nouă.
6. Backfillul este bounded, resumable, observabil și separat de tranzacția de deploy dacă depășește
   bugetul. Nu ține lock nebounded pe hot tables.
7. În incident se revine la imagine/config; nu se face down migration distructivă. Contract/drop
   apare într-un release ulterior după ce rollback window s-a închis.

## Disaster recovery

### Surse de adevăr după Stage 1

| Componentă | Autoritativ pentru | Pierdere/recovery |
|---|---|---|
| Postgres | `web_turns`, messages/state, cart/receipts, feedback, tenant config | backup+PITR; restore izolat și verificat |
| Redis | acceleration/coordination conform NX-233 | pierderea nu poate pierde un turn web deja acceptat; sweeper reclaims din Postgres |
| GHCR + release manifest | exact image/config compatibility | redeploy după digest semnat, fără rebuild |
| OTel backend | operațional, nu adevăr comercial | gap devine alert/UNKNOWN, nu blochează recovery |
| secret store | credentialele curente/previous | restore + rotație/revocare controlată |

### Targete și condiții

- **Postgres RPO target ≤5 minute, RTO target ≤60 minute.** Sunt `UNVERIFIED` până când planul
  providerului și un PITR drill cu timestamps demonstrează efectiv targetul.
- **Aplicație/config RPO 0 pentru release committed, RTO ≤15 minute dacă DB/TLS sunt sănătoase**,
  demonstrat prin redeploy al digestului într-un host/namespace curat.
- **Redis customer-result RPO 0** după acceptul durabil: acceptul se reconstruiește din ledger;
  target de reluare executor ≤10 minute, măsurat în loss drill.

Runbookul acoperă: DB indisponibil/corupt, restore PITR, Redis volume pierdut, host pierdut, registry
temporar indisponibil, secret compromis, certificate/DNS, OTel down și deploy parțial. Include owner,
severity, comenzi read-only întâi, criteriu de escaladare, comunicare, validation și postmortem.

Minimum trimestrial și înainte de launch, restorează backupul într-un DB/proiect izolat, niciodată
peste production. Verifică migration state, counts/checksums fără PII în artifact, RLS/grants,
cross-tenant denial, un replay de turn terminal și reclaimul unui turn accepted. Ștergerea mediului de
drill este explicită, aprobată și separată de scriptul care validează; cardul nu autorizează cleanup
automat al producției.

## Failure matrix obligatorie

| Failure/atac | Comportament obligatoriu | Rollback/alert |
|---|---|---|
| tag `latest` mutat | deployul ignoră tagul, verifică digest+signature | abort înainte de pull/up |
| image/SBOM/provenance lipsă | promotion FAIL | păstrează champion |
| CVE critical/high fără excepție validă | build/release FAIL | update/policy review |
| action SHA/base digest schimbat | review explicit; nu update silent | champion intact |
| host key diferit | SSH fail-closed | incident security, nu `StrictHostKeyChecking=no` |
| secret absent/invalid | startup fail cu reason safe | nu primește trafic |
| secret apare în log/inspect/artifact | release blocat și credential revocat | incident + rotate |
| schema prea veche/nouă | readiness 503, zero trafic | migration/previous compatible image |
| migration lock ocupat/partial | job unic abort/resume conform status | fără al doilea migrator |
| previous image incompatibil cu schema | deploy blocat înainte de production | expand/contract fix separat |
| DB down după start | ready false, live true; turn accept behavior conform ledger contract | alert/bounded recovery |
| Redis volume pierdut | accepted turns reclaimed din Postgres, fără dublu LLM/action | NX-233 sweeper + SLO alert |
| OTLP down | ready rămâne conform classification; exporter drops vizibile | kill-switch export |
| smoke v2 eșuează | promotion/canary stop | previous digest/config |
| new container nu devine ready | Traefik nu routează; timeout bounded | restore previous service/digest |
| deploy întrerupt la jumătate | reconciliere idempotentă din manifest | resume sau previous digest |
| GHCR indisponibil | instanța curentă continuă; cache digest verificat doar dacă policy permite | nu rebuild pe VPS |
| restore backup corupt/incomplet | drill FAIL, RPO/RTO unverified | escalate provider; launch block |
| secret compromis | revoke/rotate dual-key unde necesar, audit safe | runbook + incident owner |

## Test Cases

### Static/supply-chain

- toate `uses:` pin-uite la SHA; workflow permissions minimale și no untrusted PR secret access;
- Docker history/context/SBOM nu conțin `.env`, keys, source credential sau unexpected files;
- dependency hashes reproducibile; tampered wheel/lock și unsigned image sunt respinse;
- vulnerability/secret scan fixtures produc failure real, nu warning verde.

### Container/health

- container rulează non-root, read-only, cap drop, no-new-privileges și limits; încearcă write/escalation;
- SIGTERM în timpul unui turn respectă grace/fencing și resultul rămâne recoverable;
- live vs ready vs startup: DB down, Redis down conform NX-233 classification, schema stale, bad config,
  pool exhausted și OTLP down;
- health response nu conține DSN, host intern, exception, tenant sau secret;
- worker heartbeat stale/dead process este detectat, fără a muta un turn de business.

### Deploy/migration

- schema fresh→latest și previous→latest pe Postgres 16 real/efemer;
- două migration jobs concurente: unul câștigă, celălalt abort safe;
- previous image rulează pe schema expanded; rollback config/digest este determinist;
- staging smoke: bootstrap, accept, status, terminal non-empty, replay exact și feedback/trace seam;
- corrupted manifest, wrong repo signature, wrong digest și missing artifact blochează înainte de host.

### DR/security

- cross-tenant/RLS după restore; `bot_runtime` nu poate migra sau citi alt tenant;
- Redis flush/loss cu accepted/running/completed turns; zero pierdere/duplicare de efect;
- restore verifier măsoară backup timestamp→restore point și service recovery, fără PII în report;
- rotație current+previous pentru session/action; revoked key nu mai semnează;
- log/artifact capture cu secrete canary produce zero matches.

## Manual drive

PR-ul include output redacted și timestamps pentru:

1. Build → digest → SBOM/provenance/signature → verification pe același digest.
2. Deploy într-un namespace/host staging curat fără `git pull`; `docker inspect` confirmă digestul.
3. Startup cu secret lipsă și schema incompatibilă: no traffic, error safe.
4. Web v2 smoke complet + retry exact, apoi OTLP down și Redis loss/restart.
5. Rollback la previous digest/config cu schema rămasă expanded; măsoară timpul până la ready.
6. Restore Postgres într-un proiect izolat, rulează `scripts/migrate.py --check`, RLS/grants, turn replay
   și accepted-turn reclaim; calculează RPO/RTO real.
7. Caută valorile canary în git diff/history relevant, image layers, `docker inspect`, logs și artifacts.

Nu se rulează delete volume, restore peste production, rotate/revoke real sau rollback live fără
aprobarea separată a userului.

## Metrics și release evidence

- readiness transitions și reason codes, deploy start/end/outcome, release SHA/digest/config/schema;
- migration duration/outcome/lock wait, smoke duration/outcome, rollback duration/outcome;
- container restart/OOM, worker heartbeat/lag, DB/Redis availability conform classification;
- backup age, last verified restore, measured RPO/RTO și drill status;
- vulnerability counts/exceptions expiry, signature/provenance verification;
- toate secretele/hosturile/IDs sunt excluse; deploy markerul este label allowlisted.

Evidence packetul este immutable și leagă CI run, digest, signature, SBOM hashes, scan verdict,
staging smoke, migration compatibility, readiness, DR status și approvals. Lipsa unui element critic
produce `NOT_READY`, nu checkbox manual fără dovadă.

## Rollout și rollback

1. Introdu health endpoints/probes și manifestul cu comportamentul curent, fără a schimba routingul.
2. Activează hardening/container și artifact build în CI; păstrează deployul vechi disabled ca fallback
   documentat numai până la primul staging success.
3. Treci staging la digest promotion; rulează migration compatibility, smoke și fault drills.
4. Verifică restore/secret rotation dry-run și targetele RPO/RTO. Dacă sunt unverified, NX-249 rămâne blocat.
5. Production folosește același digest după approval; NX-249 începe cu cohort minim, nu 100%.

Rollbackul este manifest-driven și time-bounded: oprește promotionul, setează previous digest/config,
reconciliază Compose, așteaptă ready și rulează smoke/replay. Nu șterge ledger/results și nu face
down migration în incident. Dacă schema a depășit compatibility range, rollbackul este declarat
imposibil înainte de deploy și releaseul se blochează.

## Definition of Done

- [ ] Build once/promote by digest este real; production nu consumă `latest` și nu face build/git pull.
- [ ] Image digest, SBOM, provenance și signature sunt generate și verificate înainte de deploy.
- [ ] Actions/base/dependencies sunt pin/lock/hash verificate; scans fail-closed cu excepții expirabile.
- [ ] Workflow permissions, environments, approvals, SSH host trust și deploy user sunt least-privilege.
- [ ] Niciun secret/admin DB credential nu există în image, repo, args, logs, inspect sau artifacts.
- [ ] Containerul este non-root/read-only/cap-drop/no-new-privileges și are limits/shutdown corect.
- [ ] Live/startup/ready și worker health testează semantics reale, fără model call sau data leak.
