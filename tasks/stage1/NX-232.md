## Outcome verificabil

Un turn web acceptat are un ID stabil și un rând durabil, iar `(tenant, conversation,
client_turn_id)` este idempotent. Pierderea răspunsului HTTP, refreshul, retry-ul, restartul și două
taburi întorc același rezultat terminal fără un al doilea apel LLM sau o a doua mutație.

## Existing state și finding reproductibil

- Frontendul real trimite deja un `client_msg_id` UUID.
- `processor.py:332-334` tratează duplicatul ca `deduped=True` și `reply=None`.
- `/web/chat` randează acel rezultat ca payload gol; idempotency actuală înseamnă drop, nu replay.
- NX-221 adaugă lock Redis best-effort, cu bypass la timeout/Redis down; nu persistă rezultatul.
- Nu există endpoint de lookup/recovery și UI nu poate corela un turn pending.

NX-221 este reutilizat ca optimizare temporară, dar ledgerul DB devine garanția de corectitudine.

## Boundary frontend — nenegociabil

Frontendul generează/persistă `client_turn_id` și cere resultul. Nu decide dacă un retry este un turn

## Schema logică `web_turns`

Coloane minime (numele finale se aliniază convențiilor repo):

- `id`, `business_id`, `conversation_id`, `contact_id`, `session_id/ref`;
- `client_turn_id`, `request_fingerprint` HMAC/safe, `schema_version`;
- `status`: `accepted|running|completed|failed|cancelled`;
- `attempt`, `lease_owner`, `lease_epoch`, `lease_expires_at`, `deadline_at`;
- `conversation_revision_at_accept`, `pipeline_version`;
- `response_json` numai ViewModel validat sau error-view terminal;
- `safe_error_code`, timestamps și retenție;
- opțional `action_id`/receipt refs, fără raw message/token/PII.

Constrângeri:

- UNIQUE `(business_id, conversation_id, client_turn_id)`;
- request fingerprint conflict pentru același ID + alt input → 409;
- partial UNIQUE un singur `accepted|running` per conversație, cu policy explicit pentru active turn;
- FK/indexuri tenant-safe și RLS;
- `completed|failed|cancelled` implică `response_json` randabil;
- status transitions prin compare-and-set + `lease_epoch` fencing.

### Mapping ledger intern → status wire v2

Ledgerul păstrează enumul intern exact `accepted|running|completed|failed|cancelled`; nu adaugă
`working` sau `validating` ca stări DB concurente. Proiecția NX-233 către contractul NX-228 este:

| Ledger/phase server-owned | `turn.status` wire |
|---|---|
| `accepted` | `accepted` |
| `running`, execuție normală ori phase indisponibil după recovery | `working` |
| `running` și validatorul rulează efectiv | `validating` |
| `completed|failed|cancelled` | aceeași valoare, cu `response_json`/blocks randabile |

Frontendul nu deduce phase-ul din timp/text și nu vede `running`. `validating` este o proiecție
server-owned reală, nu o tranziție nouă a ledgerului și nu un timer cosmetic. Replayul terminal
returnează exact ViewModelul persistat, inclusiv statusul terminal.

## Failure/concurrency matrix

| Caz | Rezultat obligatoriu |
|---|---|
| același ID + același request, active | același `turn_id`, status curent |
| același ID + același request, completed | același `response_json`, byte-equivalent canonical |
| același ID + alt request/context | 409 `idempotency_conflict` |
| două inserturi simultane | un singur rând/turn |
| worker moare cu lease | reclaim după expiry, epoch nou |
| worker vechi finalizează după reclaim | update 0 rows; rezultat respins |
| commit reușește, HTTP se pierde | GET/retry replayează rezultatul |
| DB commit eșuează | niciun message/state/result parțial |
| alt tenant/contact cere ID-ul | 404/403 fără existence leak |
| terminal response invalid/gol | commit refuzat; safe error-view persistat |
| proiecția expune `running` pe wire sau inventează `validating` | contract violation; mappingul server este singurul owner |
