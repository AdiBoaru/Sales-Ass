## Boundary frontend — nenegociabil

Diagrama 04c arată frontendul ca transport/decoder/renderer/UI lifecycle, nu ca motor conversațional.
Muchiile permise sunt: raw text sau action token opac spre backend; bootstrap/status/result spre
decoder; ViewModel valid spre registry; UI event tehnic spre controller; href valid spre navigare.

Nu desena în frontend intent, routing, retrieval, ranking, memory merge, price/stock/discount/total,
cart mutation, semantic chip parsing, greeting/disclaimer/fallback/progress inventat ori release
assignment. Dacă un astfel de edge încă există în buildul final, nu-l cosmetiza: marchează-l
`NON-COMPLIANT` într-un finding și blochează afirmația că Stage 1 este as-built complet.

## Topologia obligatorie a diagramelor 04

Numele finale pot include titluri mai descriptive, dar identificatorii 04a/04b1/04b2/04b3/04c și
separarea de mai jos sunt stabile.

### 04a — Web ingress, durability, serialization și recovery

Trebuie să urmărească: browser/host tokens → edge NX-229 → structural/body cap → privacy NX-230 →
admission → `accept_turn` ledger → 202/replay/conflict → wake-up + DB sweeper → claim/lease/epoch →
executor → terminal commit → GET/SSE projection/recovery. Include două taburi, response loss, restart,
deadline și terminal error-view. Arată explicit că Postgres este authority, Redis este wake/optimization
conform codului final și SSE nu este authority.

### 04b1 — TurnSnapshot, state/reference și alegerea căii

Trebuie să urmărească: rehidratarea ID-only page/cart → `TurnSnapshot` → `ConversationStateV2` reducer
și reference precedence → action kernel/fast path exact → single principal agent când fast path nu
poate răspunde sigur. Arată privacy form la fiecare boundary, `UNKNOWN ≠ MISMATCH`, revocări/corecții,
state revision și faptul că frontendul nu furnizează facts/tenant.

### 04b2 — Query/search/tools, EvidenceBundle și AnswerPlan

Trebuie să distingă exact agent rounds, total tool-call budget și search-call budget; să arate
`QuerySpec`/`search_entities`, lexical/semantic/fusion/fallback, hard filters, hydration/version,
EvidenceBundle, tool results și AnswerPlan. Orice fast path/agent branch are evidence contract propriu.
Nu desena `spec_numbers`, reranker, critic sau tool dacă simbolul/call-site/testul final nu-l dovedește.

### 04b3 — Validation, projection și atomic result

Trebuie să urmărească: AnswerPlan/structured facts → deterministic claim/evidence validation → critic
selectiv unde chiar există → retry/fallback bounded → WebViewModel projector → schema/URL/action/cart
receipt/P6 validation → `TurnCommit` atomic cu state/messages/receipts/result → aftercare post-commit.
Recommendation, comparison, no-result, order și action trebuie să convergă prin final gate-ul real sau
să fie desenate ca excepții explicite, nu conectate fictiv.

### 04c — Frontend pasiv și lifecycle single-flight

Trebuie să urmărească: bootstrap/session/context handles → controller singleton → stable
`client_turn_id` înainte de I/O → POST accept → SSE/poll/GET recovery → strict decoder/hash → reducer
tehnic → registry finit în ordinea backend → blocks/actions/navigation → terminal apply înainte de
unlock. Include refresh, route remount, offline, two-tabs invalidation/refetch, a11y/live region și
controls disabled în toate stările neterminale. Fără token streaming/CoT/progress timer.

### V1 legacy — separat, nu overlay

V1 primește propria secțiune mică, cu statusul real după NX-249, endpoint/render path, rollback window
și limitările cunoscute. Nu folosi aceeași culoare/legendă „live v2”. Nu desena o muchie magică
v1↔v2 în frontend. Dacă v1 este disabled dar code-retained pentru rollback, acestea sunt două fapte
distincte și ambele se notează.

## Registrul de dovezi node/edge/invariant

În același document sau în `docs/architecture/04-EVIDENCE.md`, creează un tabel machine-reviewable
cu câte un rând pentru **fiecare** node și edge din Mermaid:

| Câmp | Conținut obligatoriu |
|---|---|
| `diagram_id` / `element_id` | de ex. `04a` / `EDGE_ACCEPT_LEDGER`; IDs stabile, unice |
| claim | o singură proprietate observabilă, fără „și” care ascunde mai multe garanții |
| runtime status | `LIVE_V2`, `DEGRADED`, `OPTIONAL`, `LEGACY_DISABLED`; fără `PLANNED` în as-built |
| code evidence | path + symbol/call-site la SHA; line number numai ajutor, nu identitate |
| test evidence | path + test name și ce demonstrează exact |
| operational evidence | script/run ID/digest când testul nu dovedește deploy/recovery |
| semantics | sync/async, authority/projection/cache, at-least-once/idempotent/atomic/best-effort |
| failure edge | reason code/fallback/deadline și destinația terminală |
| privacy/tenant | forma safe și sursa server-owned `business_id` |
| verified at | backend SHA, frontend SHA, image digest, data/config version și dată |

Coverage obligatoriu: 100% nodes, 100% edges și 100% invariants enumerate. Un test generic
`pytest passed` nu este evidence pentru fiecare claim. Un test poate susține mai multe rânduri numai
dacă asserts relevante sunt identificate. Muchiile care reprezintă doar fallback intent trebuie fie
eliminate, fie marcate explicit ca `TARGET/NOT LIVE` în altă secțiune — niciodată în flowul as-built.

## Semantica de livrare — vocabular obligatoriu

Folosește această taxonomie consecvent în diagrame și runbookuri:

| Frontieră | Afirmația permisă dacă dovezile Stage 1 o confirmă | Afirmație interzisă |
|---|---|---|
| browser POST/retry | transport poate fi at-least-once; `client_turn_id` face acceptul idempotent | „request exactly once” |
| DB accept/claim | insert/claim CAS, maximum un owner fenced autoritativ la un epoch | „worker rulează o singură dată” |
| Redis wake/SSE event | best-effort/at-least-once notification; DB lookup/recovery este authority | „Redis garantează resultul” |
| pipeline după crash | attempts pot fi repetate; stale commit este fenced | „LLM/tool call exactly once” |
| internal `TurnCommit` | atomic all-or-nothing pentru rows incluse în aceeași tranzacție | atomicitate peste API extern |
| action/cart extern | idempotency key + receipt; garanția exactă a adaptorului se declară explicit | „exactly-once commerce” generic |
| terminal result GET/SSE | replay idempotent al aceluiași ViewModel; delivery poate fi repetată | „client vede o singură livrare” |
| feedback | write idempotent/revisionat pentru promptul autorizat | „un singur click posibil” |
| OTel/events | best-effort bounded, cu gaps vizibile | telemetry ca source of truth |

Dacă providerul extern nu oferă idempotency, diagrama notează „at-least-once call, dedupe/receipt
limit” și runbookul explică reconcilierea. Nu transforma „exactly-once effect” într-o promisiune prin
faptul că DB commitul local este atomic.

## Test Cases

### Coverage/linkage

- parsează Mermaid pentru toate cele cinci diagrame și produce zero syntax errors;
- fiecare node/edge ID apare exact o dată în registrul de evidence;
- fiecare code path/symbol și test path/test name există la SHA-ul declarat;
- fiecare P0 invariant are minimum un test executabil și un manual/failure drive relevant;
- edge labels corespund condițiilor reale (`if/return/exception/status`), nu descrierii din card.

### Drift obligatoriu

- urmărește explicit TVAL invalid category până la rezultatul terminal real;
- numără rounds, tool calls și search calls cu testele NX-241, fără expresia ambiguă „max 3 searches”;
- capturează rich input și demonstrează dacă `spec_numbers` intră sau nu;
- rulează un claim greșit pe produsul corect și verifică validatorul claim↔evidence;
- capturează PII la moderation/storage/history/model/trace boundaries;
- dovedește reachability pentru AGUARD/CTAB/GRND sau le elimină/mută legacy;
- rulează comparison prin final gate și un action chip byte-identic end-to-end.

### Delivery semantics

- response loss + retry: accept/result idempotent, transport repetabil;
- worker crash după model/tool și reclaim: attempt poate repeta, stale commit fenced;
- Redis wake loss/SSE duplicate: DB lookup recuperează același result;
- external action timeout/retry: documentează receipt/idempotency limit real;
- OTel down: turnul continuă și telemetry gap nu devine authority.

### Documentation consistency

- `rg` nu mai găsește headingul vechi `Diagram 4b — Agent Stage Internals` ca descriere normativă;
- referințele normative indică 04a/04b1/04b2/04b3/04c și as-built SHA;
- termenii `exactly-once`, `max 3 searches`, `raw history`, `TVAL`, `AGUARD`, `CTAB`, `GRND` au fie
  definiție/evidence corectă, fie context `historical/legacy`;
- v1 nu apare în subgraphurile live v2 și are status/config/rollback window explicit.

### Gate repository read-only

Rulează gate-ul complet ca să dovedești că SHA-ul documentat rămâne verde, deși PR-ul este docs-only:

## Metrics și criterii de calitate ale documentului

Acest card nu adaugă metrici runtime. Raportează numai quality counters docs:

- total/covered/unverified nodes, edges și invariants per diagram;
- live/optional/degraded/legacy counts;
- code+test+operational evidence coverage;
- stale/broken links și Mermaid render errors;
- historical docs annotated versus normative docs updated;
- findings P0/P1 descoperite și cards deschise.

Prag de acceptare: 100% elemente din flowul live au code evidence; 100% P0 invariants au test și
failure/manual evidence; 100% edges au semantică; 0 `UNKNOWN` prezentat drept live; 0 parse/link error.

## Rollout și rollback

Publică documentația numai după ce production/cutover SHA este stabil și evidence registry este
verificat. Fiind docs-only, rollbackul este revertul PR-ului docs, fără atingerea producției. Dacă
production se schimbă între audit și merge, rebasează și reverifică elementele afectate; nu publica
o diagramă „aproape corectă”.

Un finding de implementare nu este rezolvat prin culoare/notă: cardul se blochează, se livrează fixul
într-un PR separat, se rerulează gates NX-247–249, apoi NX-250 continuă pe noul SHA.
