## Outcome verificabil

Pentru fiecare turn WebWidget există o urmă coerentă `request → accept → queue → execution →
model/tool/retrieval → validation → durable result`, legată de `turn_id`, fără text, tokenuri sau PII.
Sistemul publică metrici cu cardinalitate controlată, produce rapoarte SLI/SLO reproductibile și
degradează fără a afecta răspunsul dacă observability este indisponibilă.

Feedbackul de tip one-tap este autorizat, idempotent și durabil; nu este doar stare locală în UI și
nu este numit „CSAT” înainte să existe volum și metodologie suficiente. În plus, promovarea unei
schimbări care afectează răspunsul este blocată de un eval web multi-turn: journey-uri reale,
grounding determinist, rubrici umane blind și comparație pairwise champion-versus-candidate pe un
holdout sigilat. „Sună ca un om” devine un criteriu măsurabil, nu o impresie din demo.

## Existing state și finding reproductibil

- `src/worker/runner.py` măsoară local durate și `TurnContext.emit()` corelează evenimente prin
  `turn_id`, dar nu există un trace distribuit care supraviețuiește acceptului asincron/restartului.
- `analytics_events` este append-only și util pentru business events/cost, nu un substitut pentru
  metrici operaționale, histograme, sampling și burn-rate.
- Nu există SDK/exporter OpenTelemetry configurat, contract de atribute, protecție explicită de
  cardinalitate sau test care dovedește că exporterul căzut nu încetinește turul.
- Contractul curent nu are un write-side backend complet pentru thumbs/reason; deci un control
  randat de widget nu produce încă un semnal tenant-safe, idempotent și utilizabil la rollout.
- Există golden tests, qrels și harnessul NX-210/H3. Acestea se reutilizează pentru grounding și
  hard constraints, dar nu acoperă încă un journey web complet cu page/cart context, corecții,
  referințe ordinale, naturalețe, helpfulness, trust și overtalk.
- Nu există un artefact unic care calculează denominatorul SLI, bugetul de eroare și verdictul
  release; în consecință un dashboard „verde” poate ascunde răspunsuri goale sau un cohort slab.

## Boundary frontend — nenegociabil

Frontendul rămâne renderer și transport pasiv. Backendul livrează promptul de feedback, labelurile,
ordinea și acțiunile `submit` prin blocurile `text`/`action_row` deja allowlisted în NX-228. Fiecare
control conține un `action_token` opac; widgetul îl retransmite neschimbat și afișează receiptul ori
error-view-ul primit.

Frontendul **nu**:

- transformă thumbs-up/down în reason codes sau scoruri;
- construiește endpoint payload din product/message semantics;
- decide eligibilitatea, samplingul, frecvența, cohortul sau dacă un vot poate fi schimbat;
- calculează CSAT, SLO, win-rate, latency ori „confidence”;
- păstrează feedbackul ca adevăr în `localStorage` și nu antrenează nimic din browser;
- adaugă copy de mulțumire/fallback ori trimite transcript, pagină sau coș în telemetry.

Singura stare locală permisă este tehnică: control pending/disabled și randarea receiptului
server-owned. Acest card nu cere niciun PR în repo-ul frontend.

## Contracte și ownership obligatorii

### 1. Context de trace

- La edge se creează un root span server-owned. Un `traceparent` public nesemnat nu devine părinte
  autoritativ; poate fi respins sau legat numai după validare conform threat modelului NX-229.
- La accept se persistă în ledger numai contextul W3C minimal necesar continuării async
  (`traceparent` server-generated și, dacă este folosit, `tracestate` allowlisted și bounded).
- Workerul extrage contextul, creează spanul de execuție și păstrează `turn_id` ca atribut de trace,
  nu ca label de metrică. Reclaimul este un nou attempt span legat de trace/turn.
- `request_id`, `turn_id`, `client_turn_id` și tenant reference nu sunt expuse ca metric labels.
  Dacă apar în traces/loguri, sunt server-owned, validate și supuse retenției; nu se exportă body.
- Rezultatul către browser nu expune trace/span IDs interne. Corelarea suportului se face cu ID-urile
  publice deja prevăzute de NX-228.

### 2. Taxonomia minimă de spans

Runnerul/executorul deține instrumentarea; stagiile de business nu importă exporterul și nu decid
samplingul. Numele sunt stabile și fără valori dinamice:

```text
web.turn.accept
web.turn.queue_wait
web.turn.execute
web.context.load
web.fast_path
web.agent.call
web.tool.call
web.retrieval.lexical
web.retrieval.embedding
web.retrieval.fusion
web.evidence.hydrate
web.answer_plan
web.validate
web.view_project
web.result.commit
web.aftercare.schedule
```

Fiecare span are status standard OTel și atribute din allowlist: `service`, `env`, `release_sha`,
`pipeline_version`, `schema_major`, `stage`, `outcome`, `safe_error_code`, `attempt_bucket`,
`model_role`, `model_id` exact, `tool_name` din registry, `cache_result`, `release_track`. Sunt
interzise promptul, completionul, query-ul, URL-ul complet, product/customer/order ID, action token,
session token, exception body sau args/results de tool. Exception recording trece prin sanitizer.

### 3. Metrici low-cardinality

Contractul minim, cu unități și buckets documentate:

- `web_turn_requests_total{outcome,release_track}`;
- `web_turn_accept_duration_seconds`;
- `web_turn_queue_wait_seconds{attempt_bucket}`;
- `web_turn_execution_seconds{route_mode,outcome}`;
- `web_turn_end_to_end_seconds{turn_class,outcome,release_track}`;
- `web_turn_terminal_total{status,safe_error_code,release_track}`;
- `web_turn_replay_total{result_status}` și `web_turn_idempotency_conflict_total`;
- `web_turn_reclaim_total`, `web_turn_fenced_completion_total` și `web_turn_deadline_total{stage}`;
- `web_model_calls_total{model_role,model_id,outcome}` + latency/tokens/cost buckets;
- `web_tool_calls_total{tool_name,outcome}` + latency;
- `web_retrieval_outcomes_total{mode,outcome}` și validator/critic/fallback counts;
- `web_feedback_submissions_total{rating,reason_code,outcome,release_track}`;
- `web_observability_dropped_total{signal,reason}` și exporter queue/flush health.

`business_id`, `conversation_id`, `turn_id`, IP, visitor, product, free-form error și URL sunt
interzise în labels. Tenant drill-down se face prin query tenant-scoped pe datele durabile autorizate,
nu prin explozia cardinalității Prometheus.

### 4. Feedback write-side

Backendul emite un `feedback_prompt_id` random și două/mai multe action tokens cu purpose explicit,
legate criptografic de `business_id`, sesiune, conversație, turn, schema version, expiry și nonce.
Browserul nu vede claims. Endpointul autorizat acceptă numai tokenul opac plus identificatorul tehnic
de request/idempotency prevăzut în contract; ratingul/reasonul vin exclusiv din tokenul serverului.

Persistența minimă este normalizată și tenant-scoped:

- `business_id`, `feedback_prompt_id`, `turn_id`, `conversation_id`;
- `rating` allowlisted (`positive|negative`) și `reason_code` din taxonomie versionată;
- `source=web_widget`, `schema_version`, `release_sha/pipeline_version`;
- `revision`, `created_at`, `updated_at`; fără body, comment, IP, token sau identity raw.

Există un singur feedback activ per prompt/turn. Retry identic întoarce același receipt; o corecție
autorizată actualizează determinist rândul și incrementă `revision`, fără dublare în agregate. Tokenul
altui tenant/session/turn, expirat, tampered sau deja revocat este fail-closed. Feedbackul nu modifică
răspunsul curent, rankingul ori promptul online și nu devine automat training data.

Folosește tabelele existente numai dacă pot impune aceste invariants, retention și RLS. Altfel,
creează migrarea cu numărul liber rezervat la implementare și actualizează `schema_reference.md`.
Nu numi proporția de voturi pozitive „CSAT”; publică `positive_feedback_rate` cu `n` și interval de
încredere, iar la volum insuficient raportează `insufficient_sample`.

### 5. Contract SLI/SLO

Toate denominator rules sunt cod, testate și versionate în `slo_policy.v1`; dashboardul nu
redefinește formulele:

| SLI | Denominator | Numerator / măsură | SLO/gate Stage 1 |
|---|---|---|---|
| accept availability | requesturi web v2 autentificate, valide și sub rate-limit | 202/200 accepted sau replay, fără 5xx | ≥99,9% rolling 7d după canary; înainte se raportează baseline |
| durable terminal | turnuri acceptate, inclusiv reclaimed | terminal durabil și randabil până la `deadline_at + recovery_grace` | ≥99,5% rolling 7d; 100% în release suite |
| non-empty/P6 | toate turnurile terminale | ViewModel valid, minimum un bloc randabil | 100%; orice violare blochează release |
| latency | turnuri completed, pe `turn_class` și release track | accept→durable terminal p50/p90/p95/p99 | p90 sub pragul ratificat în NX-241; nu inventa prag local |
| idempotency | retry-uri cu aceeași cheie/fingerprint | același `turn_id` și rezultat, zero execuție nouă | 100% în E2E; orice conflict greșit blochează |
| grounding safety | cazurile de release eligibile | zero fapte comerciale/hard constraints neverificate | 100%; zero tolerance |

Invalid input, auth/origin reject, explicit rate-limit și user cancellation se raportează separat și
nu sunt ascunse în availability. Internal failure, timeout, exporter bug sau deploy error rămân în
denominator. Orice excludere nouă cere versiune de policy și review.

Rapoartele includ window, UTC boundaries, release SHA, sample `n`, missing-data indicator și
completeness. Lipsa datelor, clock skew, exporter gap ori denominator zero dau verdict
`UNKNOWN/INSUFFICIENT`, niciodată `PASS`. Burn-rate multi-window (1h/6h și 6h/3d) este calculat din
error budget; routingul alertei este conectat în NX-248.

## Gate de calitate conversațională „personal shopper”

### Corpus de web journeys

Construiește un format versionat în care fiecare journey are 2–6 ture, snapshot de catalog fix,
locale, page/cart IDs, state inițial, inputurile userului, facts/constraints obligatorii, acțiuni
permise și criterii de succes. Corpusul de development și holdoutul conțin obligatoriu:

1. typo/diacritice și formulări colocviale;
2. follow-up eliptic („și ceva mai ieftin?”);
3. corecții care înlocuiesc criterii vechi („nu, fără parfum”);
4. clarificare utilă când informația chiar lipsește, fără interogatoriu inutil;
5. referințe ordinale/deictice („primul”, „acesta”, „compară-le”);
6. page context și schimbare de pagină între ture;
7. hard constraints, inclusiv `UNKNOWN ≠ MISMATCH` și safety;
8. no-results cu relaxare explicită/onestă sau cale concretă, fără produse inventate;
9. cart snapshot, mutație cu receipt și cart stale/conflict;
10. conversații mixte: greeting → recomandare → comparație → acțiune.

Minimum pentru gate: cel puțin 60 journey-uri de development și 40 journey-uri sigilate, fiecare
familie prezentă de minimum patru ori în holdout și minimum 30% din holdout adversarial. Acestea sunt
minime de acoperire, nu ținte de produs; ownerul poate crește setul fără a relaxa pragurile.

În repo intră corpusul development, schema, runnerul și `holdout_manifest.json` cu `suite_id`, număr,
distribuție și SHA-256. Conținutul/expected answers din holdout stau într-un store/artifact restricționat.
Runnerul verifică hashul înainte de execuție și nu printează transcriptul în CI artifacts.

### Evaluare deterministă înaintea judecății de stil

Pentru fiecare tur se verifică mai întâi: schema ViewModel, terminal non-empty, evidence/provenance,
preț/stoc/link/variant, hard constraints, safety, state delta, reference resolution, action scope,
receipt și absența PII. Orice failure hard marchează întregul candidate `FAIL`; un judge nu poate
compensa o halucinație cu un scor bun de ton.

### Rubrică umană blind și pairwise

Minimum doi evaluatori independenți, fără release/model labels, văd aceeași stare vizibilă unui
shopper și răspunsurile A/B în ordine randomizată. Evaluează cu ancore publicate 1–5:

- **naturalness:** română firească, continuitate, fără ton robotic/meta;
- **helpfulness:** răspunde direct și avansează cumpărarea fără pași inutili;
- **trust:** este onest despre necunoscut, nu exagerează și justifică prin fapte relevante;
- **no overtalk:** lungimea/numărul de opțiuni sunt proporționale cu întrebarea;
- **context handling:** ține corecțiile, referințele și pagina/coșul fără contradicții.

Evaluatorul alege și `A|B|tie` per journey plus reason code allowlisted. Diferență >1 punct pe o
rubrică sau winner disagreement cere al treilea evaluator/adjudicare. Raportul arată acordul dintre
evaluatori, order-bias și rezultate pe fiecare familie, nu numai media globală.

Un LLM judge poate rula ca semnal secundar, cu `judge_model_id`, prompt hash, seed și versiune fixate,
dar nu înlocuiește blind human gate și nu vede care variantă este candidate.

### Praguri fail-closed

Candidate poate avansa numai dacă toate sunt adevărate:

- 100% pass la grounding, hard constraints, safety, PII, action/receipt și P6;
- fiecare rubrică are media ≥4,0/5 pe holdout și niciun cohort obligatoriu sub 3,8;
- rata `overtalk` sever este ≤5%; niciun pattern de disclaimer/meta repetat sistematic;
- scorul pairwise `win + 0,5×tie` este ≥55% și limita inferioară bootstrap 95% nu este sub 50%;
- niciun cohort nu are regresie >5 puncte procentuale față de champion;
- latența și costul rămân în bugetele versionate NX-241/NX-249;
- manifestul/hashul este valid și coverage complet; missing data produce FAIL, nu skip.

Dacă sample-ul nu poate susține intervalul de încredere, verdictul este `INSUFFICIENT` și nu se
promovează. Pragurile se schimbă numai prin PR de policy separat, înainte de rularea candidateului;
nu se ajustează după ce rezultatul este văzut.

### Bucla de feedback spre îmbunătățire

Săptămânal, un job/read-only report selectează stratificat feedback negativ/pozitiv și outcome-uri
tehnice, folosind numai transcript safe autorizat. Reviewul uman atribuie o taxonomie stabilă:
retrieval, constraint, context/reference, grounding, tone, overtalk, clarification, no-result,
action/cart, latency sau UI/transport. Se aleg maximum trei cauze principale; fiecare fix adaugă un
caz redacted în development regression set, rulează qrels/H3 + web journeys și nu atinge holdoutul.

Feedbackul userului nu intră direct în prompt, ranking ori fine-tuning. Nicio observație singulară
nu schimbă producția. NX-249 consumă trendurile, evidence packetul și verdictul pentru canary.

## Failure matrix obligatorie

| Failure/abuz | Comportament obligatoriu | Dovadă |
|---|---|---|
| OTLP lent/down/429 | buffer bounded, timeout/drop contabilizat; turnul continuă | fault injection + latency diff bounded |
| exporter queue plină | drop newest/oldest conform policy, counter; fără memorie nelimitată | load test |
| exception conține query/token/telefon | sanitizer înainte de record/export; testul nu găsește canary | capture exporter |
| label primește UUID/free text | API/registry refuză sau normalizează la reason allowlisted | cardinality test |
| worker restart după accept | trace continuat/linked pe același turn; attempt separat | restart drive |
| trace context public fals | nu poate atașa/otrăvi trace intern al altui tenant | security test |
| feedback retry identic | același receipt, un singur efect | concurrency/integration |
| două voturi simultane/opuse | policy deterministă, o singură revizie activă | race test |
| token feedback cross-tenant/expirat | 404/403 safe, zero write/existence leak | tenant test |
| feedback storage unavailable | răspunsul conversațional rămâne completed; feedback error-view onest | fault injection |
| feedback insuficient | `insufficient_sample`, nu CSAT/0%/100% înșelător | report test |
| ledger/event gap | SLO `UNKNOWN`/FAIL, niciodată PASS | missing-data fixture |
| clock skew/negative latency | sample invalid + counter/alert; nu intră silențios în percentile | property test |
| candidate are un preț inventat | gate hard FAIL indiferent de scorul uman | eval fixture |
| candidate natural, dar overtalk | rubrică/cohort raportat și prag aplicat | blind rating fixture |
| holdout hash diferit/lipsește | runner exit non-zero înainte de eval | CLI test |
| evaluator vede labelul candidate | artifact invalid; rerun blind | schema/provenance check |
| sample prea mic | `INSUFFICIENT`, promovare blocată | threshold test |

## Test Cases

- propagare/extragere W3C validă, context invalid/bounded și restart link;

- allowlist spans/attributes; metric label cardinality guard și buckets;

### Integration

- Postgres real: orice query feedback/eval are `business_id = $1`, RLS cross-tenant și grants
  `bot_runtime` minimale; cleanup/retention bounded;
- accept→worker→model/tool→commit produce trace complet și terminal metric o singură dată;
- replay nu dublează execution/model metrics; reclaim produce attempt nou, nu turn nou;

## Metrics, dashboards și alerts

- Dashboard operațional minim: accept rate, queue/execution/e2e percentile, terminal/P6, replay,
  reclaim/fencing, deadline, exporter drops, model/tool latency/cost, per release track.
- Dashboard de calitate: feedback `n` + interval, reason taxonomy, deterministic violations,
  rubric means/distribution, pairwise win/tie/loss și cohort breakdown.
- Alerts sunt derivate din `slo_policy.v1`; nu din thresholds copiate manual în UI.
- Fiecare panel arată freshness/completeness și release marker. No data este vizibil, nu verde.
- Linkul trace→turn este autorizat și nu expune tenant/client data unui operator neautorizat.

## Rollout și rollback

1. Landează SDK/config cu exporter OFF; verifică zero schimbare funcțională și overhead local.
2. Activează capture/in-memory în test, apoi OTLP pe staging cu sampling mic și redactare verificată.
3. Activează pe demo: 100% errors/deadlines/reclaims, deterministic sample pentru successes.
4. Pornește feedback numai după NX-236 și privacy gate; promptul este cohort/feature-flag server-side.
5. Rulează minimum o fereastră completă de baseline înainte ca SLO/feedback să blocheze deployul.
6. NX-247 validează artifactele; NX-249 controlează canary și promotion.

Kill-switchuri independente: trace export, metrics export, feedback prompt/write și eval scheduler.
Rollback oprește exportul/promptul fără redeploy dacă este sigur; păstrează rândurile feedback și
ledgerul, nu face down migration în incident și nu pierde turnuri. O versiune anterioară trebuie să
ignore în siguranță coloanele/câmpurile noi. Dacă instrumentation produce latență, exporterul se
dezactivează primul; trace local/error logs safe rămân disponibile.

## Definition of Done

- [ ] Trace-ul complet acoperă accept, queue, execution, model/tool/retrieval, validation și commit,
  inclusiv restart/reclaim, cu exact un `turn_id` canonic.
- [ ] Exporterul este bounded/non-blocking; down/slow/queue-full nu schimbă răspunsul și are probe.
- [ ] Niciun body/prompt/completion/token/PII/high-cardinality ID nu apare în metrics sau export.
- [ ] Metric names, units, labels, buckets și release markers sunt documentate/testate.
- [ ] `slo_policy.v1` definește denominatorii; missing/insufficient data nu poate produce PASS.
- [ ] SLO-urile de availability/terminal/P6/idempotency sunt calculate; latența consumă pragul NX-241.
- [ ] Feedbackul este server-owned, autorizat, tenant-scoped, idempotent și fără free text/PII.
- [ ] Nu se declară CSAT; raportul include `n`, interval și `insufficient_sample`.
- [ ] Corpusul acoperă toate journey families, manifestul holdout este sigilat și hash-verificat.
- [ ] Grounding/hard constraints/safety/P6 au zero tolerance și preced rubricile de stil.
- [ ] Pairwise blind are minimum doi evaluatori, randomizare, adjudicare și praguri fail-closed.
- [ ] Naturalness/helpfulness/trust/no-overtalk/context sunt raportate global și pe cohort.
- [ ] Feedback loop produce cases redacted în development set, niciodată self-training/holdout leak.
- [ ] Migrarea, dacă este necesară, folosește numărul liber real, RLS/grants și rollback documentat;
  cardul/implementarea nu hardcodează 039.
- [ ] Manual drive, privacy capture, DB integration și gate repository sunt verzi și atașate PR-ului.
- [ ] PR-ul enumeră config defaults, cost/overhead, dashboards, alerts, kill-switches și riscuri.
