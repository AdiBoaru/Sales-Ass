## Outcome verificabil

`search_entities` are un artefact de decizie reproductibil și unul dintre două rezultate legitime:

- **GO:** după gate-urile sealed și aprobarea umană cerută de NX-210, traseul nou este integrat live
  gradual, cu hard constraints enforce, evidence hydration, deadline și rollback instant;
- **NO-GO/NOT-READY:** feature-ul rămâne OFF, motivul și metricile sunt publicate, iar producția continuă
  pe retrievalul canonic actual fără import/execuție accidentală a candidatului.

Cardul este completabil în ambele cazuri. Stage 1 și NX-239 nu sunt blocate de un NO-GO: agentul unic
poate fi construit peste retrievalul live actual prin același `RetrievalPort`. Invariantul dur este
invers: traseul nou **nu poate fi promovat fără GO**.

## Boundary frontend — nenegociabil

Zero modificări frontend. Browserul nu trimite QuerySpec, constraints, filters, score, ranking mode,
candidate pool sau relaxations și nu reordonează/filtrează rezultatele. El afișează ordinea și reason
copy proiectate de backend. NO-GO nu activează logică de compensare în widget; fallbackul este retrievalul
canonic backend actual.

## Contract `RetrievalPort`

NX-239 trebuie să consume o interfață stabilă, nu un import direct condițional în prompt/tool code:

```text
retrieve(snapshot, runtime_query_spec, active_needs, deadline)
  -> RetrievalBundle(
       provider_version,
       candidates[refs + scores/reason codes + constraint results],
       evidence_bundle,
       coverage,
       missing_information,
       degradations,
       timing/cost metadata safe)
```

Implementări:

- `CurrentLiveRetrievalAdapter`: învelește traseul `search_products` canonic actual fără schimbare semantică;
- `SearchEntitiesAdapter`: disponibil numai în shadow/canary după gate și GO;
- selector server-side pe flag stable+pipeline version; nici modelul, nici frontendul nu îl aleg.

Hard constraints se evaluează determinist pe fiecare candidat:

- `MISMATCH` verificat pe facet ready → exclus înainte de rerank/model;
- `UNKNOWN` → nu este pretins match; rămâne separat/alternative sau declanșează maximum o clarificare;
- soft mismatch → penalty/reason code, relaxare numai conform policy explicită;
- rerankerul nu poate reînvia un hard-rejected product;
- safety/contraindication gate rămâne global și după retrieval, inclusiv pe fallback current live.

## Praguri și decizie

Pe holdoutul preregistrat și live-chain reproductibil:

- Recall@20 ≥ 90%;
- nDCG@6 ≥ 0,85;
- minimum 90% query-uri cu rezultat relevant în top 6;
- zero hard-constraint violations și zero simple-fact regressions;
- candidate P90 la/sub SLO-ul preregistrat NX-201/NX-210 și cost în budget;
- no-results/UNKNOWN/missing evidence evaluate separat, nu ascunse în media globală.

Aceste praguri nu sunt suficiente singure: NX-210 pairwise/holdout și decizia Adi rămân obligatorii.
Un tool nu poate auto-emite GO; poate emite numai `candidate_for_adi_review`/readiness.

## Pași de implementare

   NOT-READY cu blockers și sari direct la pașii de port/fallback/NO-GO; nu atinge flags live.
2. Definește `RetrievalPort`/bundle și characterization tests pentru adapterul current live. Același input
   trebuie să păstreze rezultatul actual când selectorul candidat este OFF.
3. Refactorizează shadow core în funcții reusable cu provider DB per-op; păstrează entrypointul shadow
   side-effect-free și fără registry decorator.
4. Integrează QuerySpec/needs V2 safe: hard/soft/source/operator explicit. Raw query rămâne request-scoped
   și external embedding respectă DLP/NX-225 deadline.
5. Impune rejected mask înainte și după fusion/rerank. Testează că UNKNOWN nu este exclus/pretins match.
6. Hidratează evidence și products batch, respectă published/tenant/content status și capurile; elimină
   N+1 din `_hydrate_shadow_products` dacă măsurarea arată mai multe round trips decât budgetul.
7. Rulează baseline vs candidate pe qrels/holdouturile permise; salvează manifest, hashes, flags, latency,
   cost, degradations și per-slice metrics. Nu loga queries raw/PII.
8. Dacă readiness este complet, rulează protocolul NX-210 o singură dată pe H3 și trimite rezultatul
   blind pentru verdict Adi. Software-ul nu marchează singur GO.
9. Scrie ADR `GO|NO-GO|NOT-READY`, semnat, cu rationale și fingerprint. Orice lipsă = no promotion.
10. **Pe GO:** adaugă selector shadow→1% canary→ramp, stable per business+conversation, pipeline version
    capturat la accept; current live rămâne rollback.
11. **Pe NO-GO/NOT-READY:** ține toate candidate enforce flags OFF, păstrează portul/adaptorul current,
    deschide follow-up cards din error taxonomy și marchează NX-238 complet cu verdict măsurat.
12. Rulează live-chain și fault matrix pe ambele adapters; demonstrează că NX-239 poate continua pe current.

## Failure/decision matrix

| Caz | Comportament obligatoriu |
|---|---|
| readiness H3 false | NOT-READY, feature OFF; fără import live |
| candidate sub un prag | NO-GO, feature OFF; current live rămâne canonic |
| hard violation = 1 | NO-GO indiferent de scor mediu |
| simple-fact regression = 1 | NO-GO conform protocolului |
| metrici bune, fără decizie Adi | `candidate_for_adi_review`, nu GO |
| GO semnat, flag OFF | current live; zero schimbare accidentală |
| candidate timeout/embed down | degradation bounded; fallback policy măsurată, fără hard bypass |
| reranker încearcă rejected ID | ID rămâne exclus; invariant test hard-fail |
| facet fără coverage | UNKNOWN/not-enforced; disclosure/clarify, nu MISMATCH |
| catalog/search docs version drift | run invalidat; nu compară apples-to-oranges |
| canary regression | kill switch la current live, conversațiile in-flight respectă pipeline version |
| tenant B fără embeddings | fallback current/lexical conform policy, fără query cross-tenant |

## Rollout și rollback

NO-GO/NOT-READY este rollout valid: candidate OFF, current adapter ON, artefactele păstrate. Pe GO,
deploy code dark → shadow → stable 1% canary → ramps aprobate. Selectorul este server-side și capturat
în `pipeline_version`; nu comută providerul în mijlocul unei conversații/turn. Kill switch revine în
mai puțin de cinci minute la current live fără migrare/data loss. Rollbackul nu relaxează hard/safety și
nu șterge verdictul/eval artifacts.
