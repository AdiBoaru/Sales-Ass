# NX-102 — Topic clustering: ce întreabă clienții (secțiunea 4 a raportului de cerere)
**Owner:** S · **Faza:** P2 · **Zi/Ord:** track «Cerere & Produse», Later (diferențiator) · **Branch:** `feat/NX-102-topic-clustering` · **Complexitate:** L · **Estimare:** [PROPUNERE] 6-8h → de spart (vezi mai jos)

## Goal
Secțiunea 4 a raportului «Cerere & Produse» „adevărată": grupare **semantică** a întrebărilor de
intrare într-o ierarhie topic→subtopic (ingrediente, livrare, compatibilitate, mod de folosire…),
cu volum și rezoluție per-topic — ca să afle comerciantul *ce informație le lipsește clienților*
și ce să adauge pe PDP/FAQ. Înlocuiește v1-ul grosier din NX-101 (care doar numără `faq_lookup`
miss + `clarify_asked`) cu clustere reale peste embeddings. E feature-ul premium marquee:
[ANALYTICS-AUDIT-SI-BLUEPRINT.md](../docs/ANALYTICS-AUDIT-SI-BLUEPRINT.md) §4bis (secțiunea 4) + Tier 4.

## Business Context
„38% din chat-urile pre-cumpărare întrebau despre siguranța ingredientelor → fix de conținut" e
exact genul de insight care schimbă PDP-uri și reduce frecarea de vânzare. E un diferențiator de
retenție pe care toolurile premium (Intercom Topics Explorer, Yellow.ai topic clusters) îl au, iar
noi avem deja infra pgvector — doar că nu rulează clustering pe întrebări.

## Technical Description

### Important — `intents` jsonb NU e o taxonomie de topic
`usage_daily.intents` e cheiat pe **route-ul grosier de triaj** (`simple|sales|order|handoff|clarify`),
NU pe un topic semantic. Acest task construiește o taxonomie reală, separată; nu reutiliza route-ul.

### Job offline `cluster_topics.py` (admin_conn)
1. **Selecție:** mesajele `direction='inbound'` din fereastra rulantă (ex. 90 zile), per business.
2. **Embedding:** `text-embedding-3-small` (1536, pgvector — aceeași infra ca `product_embeddings`),
   cache pe `content_hash` (re-embed doar la text schimbat). **P12:** embed pe text **normalizat/
   redactat** (fără telefoane/PII — reuse redaction-ul din logger); NU stocăm corpul brut în
   tabelele de topic, doar centroizi + etichete + contoare.
3. **Clustering:** HDBSCAN/k-means peste embeddings → clustere; etichetare cluster cu un apel
   **nano** pe câteva exemple reprezentative (label scurt, ex. „siguranță ingrediente"). Apelul de
   etichetare e **offline, în job**, nu în pipeline (P2 respectat — LLM doar la triaj/agent în
   pipeline; aici e un job de analytics, ca summarizer-ul, prin adaptorul unic).
4. **Persistare:** tabel `demand_topics` (business_id, period, topic_label, parent_label, volume,
   resolved_share, sample_count) + opțional asocierea mesaj→topic pentru drill-down (redactat).

### DB (DDL nou)
```sql
create table demand_topics (
  id            uuid primary key default gen_random_uuid(),
  business_id   uuid not null references businesses(id) on delete cascade,
  period_start  date not null,
  period_end    date not null,
  topic_label   text not null,
  parent_label  text,                          -- ierarhie topic→subtopic
  volume        integer not null default 0,
  resolved_share numeric(4,2),                 -- % rezolvate fără handoff (din join handoff events)
  created_at    timestamptz not null default now()
);
create index idx_topics_business on demand_topics(business_id, period_end desc, volume desc);
```

## Test Cases
**Happy Path:**
1. 30 mesaje pe 3 teme distincte (vectori fabricați separați) → 3 clustere cu etichete (nano mock) + volume corecte.
2. Topic cu 8/10 mesaje fără handoff → `resolved_share=0.80`.

**Edge Cases:**
1. Sub pragul de minim per cluster → mesaje în „other/necategorizat", nu clustere zgomot.
2. Re-rulare → re-embed doar la `content_hash` schimbat (cache hit pe restul).

**Failure Cases:**
1. Embed/rețea pică → job logă și sare businessul, nu oprește restul (ca `rollup_usage`).
2. Etichetare nano eșuează → cluster păstrat cu etichetă fallback („topic #N"), nu pierdut.

## Cost
**Embeddings** pe inbound nou (cache content_hash → doar delta) + **1 apel nano de etichetare per
cluster** (câteva exemple), offline. La ~N mesaje noi/zi × text-embedding-3-small (ieftin) +
~zeci de clustere × nano scurt = cost mic, controlat de: (1) fereastră rulantă + cache de embed;
(2) doar inbound (nu outbound); (3) batch nocturn, nu per-tur; (4) prag minim de cluster.
