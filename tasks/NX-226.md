# NX-226 — Rangul lexical adună două scale incompatibile: `ts_rank_cd` + `similarity` ponderat corect

**Owner:** Claude (build) / Codex (verify) · **Faza:** Web pilot (devine critic la catalog mare) · **Zi/Ord:** track C, oricând · **Branch:** `feat/NX-226-lexical-rank-scale` · **Complexitate:** S · **Estimare:** 2.5h
**Model recomandat:** Opus 4.8

## Goal
Ordinea pe `relevance` a piciorului lexical e `ts_rank_cd(...) + similarity(...)`
([catalog.py:424-429](../src/db/queries/catalog.py#L424-L429)). Problema: `ts_rank_cd`
trăiește tipic în 0.01–0.3, `similarity` (pg_trgm) în 0–1 → termenul de typo-match domină
sistematic relevanța full-text. La catalogul de azi abia se vede; la 5k+ produse decide
CINE intră în pool-ul de 50 de candidați — adică exact ce fuziunea RRF nu mai poate repara
în aval. Taskul normalizează și ponderează explicit cele două semnale, sub kill-switch,
cu verificare pe query-uri reale înainte de aprindere.

## Business Context
Piciorul lexical e jumătate din retrieval (și SINGURUL când embeddings lipsesc sau
NX-225 taie semanticul). Un clasament lexical distorsionat = produse relevante care nu
mai apucă fuziunea = recomandări mai slabe exact pe query-urile cele mai frecvente
(nume de produs + typo-uri).

## Technical Description
```sql
-- NX-226: ambele semnale în [0,1] + ponderi explicite.
-- ts_rank_cd cu flag 32 => rank/(rank+1), adică normalizat în [0,1).
-- 0.6/0.4: FTS primar (fraza naturală), trgm secundar (typo/SKU) — constante de modul,
-- nu config per business (invariant de motor, nu preferință de tenant).
0.6 * ts_rank_cd(p.search_tsv, websearch_to_tsquery('simple', ro_unaccent($q)), 32)
+ 0.4 * similarity(ro_unaccent(p.name), ro_unaccent($q))
```
- Constantele (`_LEX_W_FTS = 0.6`, `_LEX_W_TRGM = 0.4`) în `catalog.py`, cu comentariu de
  ce (scala, nu preferința). NU în DomainPack: nu e un buton de tenant, e corectitudinea
  formulei (analog RRF_K în fusion.py).
- **Kill-switch:** `lexical_rank_v2_enabled`, **default OFF** → expresia veche byte-identic.
- **Verificare empirică ÎNAINTE de aprindere (parte din card):** script read-only
  `scripts/lexical_rank_compare.py` — rulează ~20 query-uri reale RO (din `unmet_query` +
  FAQ-miss-urile cunoscute) pe tenantul demo cu formula veche vs nouă, afișează diff-ul
  de top-6 side-by-side. DOAR lexical, DOAR SELECT — zero cost LLM, zero scriere. Output-ul
  intră în PR ca dovadă; decizia de aprindere o ia Adi pe diff, nu pe teorie.
- Match-ul (`WHERE`) NU se schimbă — doar `ORDER BY`. Recall-ul identic, se schimbă doar
  ordinea candidaților.

**TurnContext:** neatins. **Cost:** zero LLM; același query SQL, expresie de sort diferită.

## Test Cases
**Happy Path**
1. Query „crema hidratanta fata" pe fixture cu match FTS pe nume+summary vs produs cu nume
   trgm-similar dar FTS zero → cu ON, primul câștigă.
2. Typo pur („sampon anti matreata" scris „sanpon") → trgm îl salvează în continuare
   (ponderea 0.4 nu omoară funcția de typo).

**Edge Cases**
1. Query care nu produce tsquery (doar stopwords) → doar termenul trgm contează → ordinea
   rămâne deterministă (tie-break `p.id` existent).
2. Toate scorurile egale → tie-break stabil pe id (neatins).

**Failure Cases**
1. Flag ON + `ro_unaccent` lipsă din DB (schemă veche) → testul de integrare pică explicit
   la boot-gate-ul de migrări, nu tăcut la runtime (verificare: migrarea 033 e în lanț).
2. Script de comparație pe business inexistent → eroare clară, exit ≠ 0, zero scrieri.

ZERO LLM în CI; scriptul de comparație e manual, read-only.
